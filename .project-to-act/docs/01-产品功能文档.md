# 产品功能文档

> 摘要自《云湃工业一体机产品设计思路文档》《完整功能文档》《完整架构文档》（2026-09-02 v0.1/v1.0）
> 与 docs/PRODUCT_AND_FUNCTION_ARCHITECTURE.md。

## 1. 产品定位

云湃工业一体机是**面向制造业的证据治理型全链路 Agent**：一个统筹 Agent 作为唯一业务
入口，以 M0 为正式数据基础，把订单、工程、物料、采购、排程、成本、非标设计连成
**可追踪、可恢复、可审计**的业务执行链。产品最小单位是可暂停/恢复/验证/交付的
**业务任务**，而非聊天回答。

### 解决的五类根问题

1. 信息重复录入（同一数据在多个系统手工重录）
2. 数据来源丢失（改完不知道原始依据）
3. 前置事实变化不重算（BOM 改了排程没跟着变）
4. AI 建议不可交付（说得好听但落不了单）
5. 经验不沉淀（人的判断没有变成系统资产）

### 六大卖点

一次对话贯穿业务链；有证据的业务执行；M0 事实基础；异常统一 Gate；受治理的自进化；
全链路追溯。

## 2. 目标用户（7 类）

| 用户 | 关注 |
|---|---|
| 工厂/运营负责人 | 全局状态、异常、交付 |
| 工程（BOM/SOP） | 文档入库、工程确认 |
| 采购 | 建议审阅、PO、供应商回复 |
| PMC/计划 | 排程、缺料、齐套 |
| 财务/审计 | 证据链、审批留痕 |
| 非标设计（M8） | ID 设计子流程 |
| 管理员/知识治理 | 权限、知识库治理 |

## 3. 五条设计原则

1. 一个根入口、一个根执行者（统筹 Agent 唯一业务入口）。
2. M0 管正式事实，模块管运行事实（M3 库存/MRP、M4 采购、M5 排程、M6 成本、M8 设计过程）。
3. 模型理解规划、确定性代码约束执行。
4. 默认自动继续，异常统一 Gate（允许/拒绝/暂停修改）。
5. 候选先缓存，3 个独立任务或强证据才晋升为正式事实。

主交互为「理解→计划→执行→校验→交付→沉淀」六段闭环；五条端到端路径：订单到计划、
查询追溯、新数据入库、经验自进化、操作自进化。

## 4. 模块功能全景（module_decls 129 个声明）

| 模块 | 工具数 | 职责与要点 |
|---|---|---|
| **M0 数据基础** | 27 | 导入七层管道（upload→status→preview→resolve→commit→rollback→history/quarantine）、canonical 发布（products/orders/boms/materials/suppliers/equipment/routes/operations/tooling 九类 import facade，单事务+Outbox）、查询（产品总览/图、文档、库存）。模板版本 `m0.product.v1`~`m0.tooling.v1`、`m0.ingest.v1`、`m0.document-candidate.v1` |
| **M1 文档解析** | 17 | 核心 `ingest_document`（`/ingest/sync`，产出 `m1.document.v2`，带 SHA-256/MIME/源坐标/置信度/证据引用）；任务/批次查询、订单/文档检索、HITL 审核、报告导出、Governed Wiki 知识五查询。parser-only，不做业务决定 |
| **M2 BOM/SOP** | 7 | 核心 `run_bom_sop_workflow`（输出 bom_generation/sop_generation/open_customer_questions，SOP 为 80806-129 格式 Word） |
| **M3 物料/MRP** | 17（3 正式+14 遗留） | 正式入口 `run_m3_procurement_requirements`（库存/在途由 Provider 自查）；`receive_m3_material_demand` 为 M5 反馈幂等受理。缺料公式 `gross=订单量×单耗×(1+损耗)`、`shortage=max(0,gross−available)` |
| **M4 采购** | 26 | 建议导入（需 tenant+site+idempotency_key）→生成 PO→审批（submit-review/approve/request-changes，均需 expected_revision+expected_checksum CAS）→邮件草稿→供应商回复 parse/confirm→tracking/alerts/催单/供应快照 |
| **M5 PMC 排程** | 20 | 核心 `solve_scheduling`（幂等键+expected_head_plan_version，pressure_only 不得发布，source_observed_at 逐来源 24h 新鲜度校验）；get/list/replan/dispatch（仅 released，无 MES sender 只回 pending）/执行摘要/知识 RAG/报工 `report_workload`（event_type: actual_start/actual_finish/quantity_report/scrap/exception） |
| **M6 成本** | 2 | 成本核算（未联调） |
| **M8 非标设计** | 1 | `run_id_design` 灰盒子 Agent（intake→id_design→validate→quality_evaluate→human_gate→persist） |
| **data-adapter** | 5 | 外部数据接入 |
| **Orchestrator 自有** | 7 | get_business_order_trace 等业务追溯查询（ORCH-001~020 共 20 项功能） |
| **M7 法务** | 0 | 未交付 |

**Orchestrator 功能（ORCH-001~020）**：统筹对话、意图路由、版本化工作流、自由 ReAct、
六类 Gate（M0 candidate、M1 低置信 review、M2 工程 engineering、M4 供应商 procurement、
M5 发布 apply、数据补充 data）、RunState 持久化与恢复、trace 审计、MCP 暴露、
business-flows 目录、知识治理入口等。

## 5. 版本演进路线

- **P0 可信执行闭环**（当前阶段）：上传识别→M0 canonical→M1-M5/PMC 真实链路。
- **P1 受治理知识**：orch_knowledge 8 张表、结构指纹聚合、3 独立任务晋升门禁。
- **P2 操作自进化**：可批准的操作模式学习。
- **P3 模块生态完善**：M7 法务、模块市场。

## 6. 与旧口径的差异（防混淆）

- 「业务模块 79 个」是历史口径，现行以 module_decls 129 声明为准。
- 仓库内旧 `frontend/`（yunpai-agent-workspace）已弃用并从统一源码移除；正式前端是
  `frontend-yunpaizhisuan/`（React19+Vite+antd，独立团队开发）。
- `m0_m5`（order_to_schedule）工作流已删除，现行两个工作流：
  `m1_m5_document_to_plan`（原始文件入口）与 `canonical_to_m5`（订单已入库后排程）。
