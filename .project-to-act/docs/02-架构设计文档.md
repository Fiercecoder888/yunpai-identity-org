## 1. 分层架构与六大结论

```
接入层（前端 / Identity BFF / 网关）
   ↓
统筹层 Orchestrator（LangGraph：ReAct + 固定业务 StateGraph、五类桥接、TaskID/幂等/Gate/恢复）
   ↓
权威数据层 M0（PostgreSQL canonical；模块不得直连其库）
   ↓
工具服务层 M1-M6（独立故障域，经 HTTP Tool / MCP 调用）
   ↓
子 Agent 层 M8 ｜ 记忆演进层（L1/L2 Redis、L3 PostgreSQL、L4 Chroma）
```

六大结论：M0 是跨模块唯一 canonical；PostgreSQL 权威、Neo4j/搜索为投影须回指
fact ID/revision/checksum；模块独立故障域；正常自动异常统一 Gate；模型理解代码约束；
一个业务任务一个根 TaskID。

## 2. 编排图（src/yunpai_langgraph/graph.py）

- 拓扑：`START → planner → worker → reviewer → worker | END`。
- RunState 生命周期：`queued → running → waiting_human → running → completed/failed`。
- 工作流（workflows/，09-06 重构后 2 个）：
  - `m1_m5_document_to_plan`（9 步）：**原始文件入口**——上传→M1 解析→review→M0
    canonical→M2→M3→M4→M5。前端原始文件上传必须发这个 workflow（发 `m0_m5` 会 415）。
  - `canonical_to_m5`（7 步）：订单已入库后的直接排程。
- 自由路径：GET/HEAD/OPTIONS 只读工具直接执行；四个主链工具可执行到审查点；
  其余非只读先过 authorization Gate。
- Gate/补充契约（实测验证）：`review/candidate/engineering/apply` 用 **approve**；
  `data` 用 **retry + supplement**；`procurement` 用 **retry + supplier_by_material**。
  把 engineering 误当 retry 会导致 M2 反复 supersede 卡死。
- M2 `run_bom_sop_workflow` 分两段 gate：先 data（补 product_code+bom_lines+routing_steps），
  匹配后开 engineering（approve 即可）。
- M3 要求 `inventory[*].received_at` 必填，缺字段服务返回 REQUEST_VALIDATION_ERROR；
  补充 inventory 须带 material_code/warehouse/lot_no/available_qty/locked_qty/qc_status/received_at。
- 失败关闭边界：不补造库存/供应商/ETA/工时/资源/审批人；pressure_only 不得发布；
  邮件草稿≠发送；授权拒绝=零工具调用，批准=恰好一次。

## 3. 数据库设计

### 目标态：M0 canonical PostgreSQL（四 schema 16 表）

| schema | 表 |
|---|---|
| core | entities / entity_versions（版本只增不改）/ entity_aliases / entity_relations |
| knowledge | source_assets / source_occurrences / evidence_anchors / field_claims / relationship_claims |
| staging | structured_records / field_candidates / identity_candidates / relationship_candidates |
| audit | audit_events / ingest_ledgers / projection_outbox |

全局约定：全表 uuid tenant_id + RLS；timestamptz 存 UTC 展示 Asia/Shanghai；摘要/指纹
char(64) SHA-256；置信度 numeric(5,4)；枚举 lifecycle_status=draft/active/inactive/retired、
approval_status=candidate/approved/rejected/expired。发布事务九步校验顺序（权限→schema→
写 entities→新增版本→来源证据→audit+ledger→同事务写 outbox→投影失败只重试不回滚→回读判定）。
person 敏感字段（姓名/身份证/工资）不得进普通查询 payload；无回读证据不得声称已落库。

### 编排层实际落地（SQLite）

| 库 | 表 | 用途 |
|---|---|---|
| `runtime/yunpai-runs.sqlite` | runs（单表 JSON 整存 RunState） | 运行状态/恢复 |
| `runtime/yunpai-business-catalog.sqlite` | ingest_batches / source_files / document_candidates / field_observations | 业务资料识别候选库；UNIQUE(absolute_path, sha256) 幂等 |
| `runtime/yunpai-m0.sqlite`（M0 后端） | import_batches / source_documents / import_candidates / approval_records / canonical_entities / canonical_entity_versions / canonical_ledger / canonical_outbox | M0 数据后端（SQLite/Postgres 双实现，schema `yunpai_m0`） |
| `runtime/yunpai-m5.sqlite` | m5_plans / m5_heads / m5_lifecycle / m5_dispatch / m5_execution_events / m5_idempotency / m5_knowledge / m5_messages / m5_outbox / m5_procurement_proposals 等 12 表 | M5 计划库（六类 snapshot+head CAS） |
| recognized_tables（YUNPAI_RECOGNIZED_DB） | — | agent 识别落库（sample_file→ingest_recognized 链路） |

## 4. Tool / MCP 体系

- 合同权威：`registry/tool-manifests/*.json` 与 `src/yunpai_langgraph/manifests/*.json`
  **必须字节一致**（tests/test_registry.py 校验 + SOURCE_PROVENANCE.json 记录 sha256；
  改 manifest 后必须更新溯源哈希）。
- 统一响应外壳 `{success, data, errors, trace_id}`；写操作透传根 X-Yunpai-Task-ID、
  租户、幂等键、trace、操作者。
- 绑定：本地 handler 在 `workers.py` HANDLERS；HTTP 模式由
  `YUNPAI_TOOL_TRANSPORT=http` + `YUNPAI_HTTP_MODULES` 显式开启；
  `LOCAL_ONLY_TOOLS = {sample_file, ingest_recognized, query_recognized_table,
  ingest_canonical}` 永不绑 HTTP；M4 由 `YUNPAI_LOCAL_M4=true` 本地执行。
- `receive_m3_material_demand`、`receive_m4_schedule_impact_proposal` 两个 receiver
  无可迁移实现，保持未绑定（fail-closed）。
- bind_http 八步：schema 校验→path 参数编码→GET/DELETE query、写 JSON body→
  content_b64 转 multipart→传播标准头→校验必需认证头→稳定错误映射→按 manifest 超时
  并复检输出 schema。
- MCP（yunpai-mcp）JSON-RPC stdio：initialize / tools/list / tools/call，仅底层
  transport，不代替 Gate。

## 5. LLM 路由（llm.py / agents.py）

- Qwen（OpenAI 兼容代理，模型 qwen3.6-35b-a3b-fp8-gpu0-200k）只提案
  intent/route/tools/confidence/reason；合法 route 仅 workflow/free/chat。
- temperature=0、enable_thinking=false、JSON response format；上下文 65536。
- 本地 ToolRegistry 为最终权威（模型提的工具名必须在册）。
- 模型不可用/超时/非法 JSON/route/工具名 → 回退确定性 Planner，标记
  `route_decision.source=deterministic_fallback`，如实留痕。
- RunState 记录 intent、route_decision、model（provider/model/base_url/status/
  latency_ms，不含密钥）。

## 6. Agent 自由化原则（09-06 确立，canonical_schema.py / tabular_extract.py 遵循）

**「语义自由，非事实自由」**：

- 交给 agent：意图路由、文件分类、字段映射、跨表推理、解释对话、新类型零代码适配。
- 绝不 agent 化：事实值（订单号/数量/交期/金额只能照抄）、计算引擎（M3 缺料、
  pmc_v2_scheduler、order_parser_v2、编码/单位换算）、护栏（magic bytes 嗅探、PII 脱敏、
  schema 校验、sha256 幂等、Gate、版本 CAS、ledger）。

三条铁律：agent 决定映射和组合，绝不编造数值；事实字段必须带 sheet/行/列/原值
_source 证据，缺失即 needs_review；输出必过确定性 schema 校验。

**落地链路（agent 驱动文件识别）**：确定性 file_sniff → `sample_file`（表头+前 10 行，
PII 身份类遮罩、工资等数值不遮）→ Qwen `map_to_canonical`（输出 kind/columns_mapping/
rows/next_tool/confidence）→ 确定性安全网 → sha256 幂等落库。confidence<0.7 进 review
（env 可配）；订单仍走 order_parser_v2 确定性解析；不做存储层 join，agent 分两次查询
自行计算；LLM 不可用回退写死规则（agent 是主路径规则是兜底）。

**BOM 全量抽取两段式**：LLM 只理解结构（entity_type + column_mapping），
`tabular_extract.extract_bom_full` 确定性遍历所有 sheet 抽全量，数值照抄不编造。

## 7. M5 PMC v2 求解语义（固定算法，不走 HTTP 不 agent 化）

- 六类 snapshot：order/routes/resource/calendar/supply/constraint，带
  snapshot_id/revision/checksum，由 canonical `build_bundle` 组装。
- **缺事实返回 `BLOCKED_INPUT`，绝不补默认值**（旧版静默补 08:00-17:00 窗口、产能 60/h、
  效率 1、APPROVED-ROUTE 的行为已全部删除——这是 P0 级修复）。
- 生命周期 draft→approved→released→dispatched；head CAS（HEAD_CONFLICT）；
  released 后不可变（PLAN_PROTECTED）；pressure_only 永不发布
  （PURPOSE_NOT_RELEASABLE）；dispatch 仅 released 且无 MES sender 时只回 pending。
- 求解器 `pmc_v2_scheduler.py` 多窗口 span（09-06 修复支持工序跨午休/跨天）；
  `pmc_wip_projection.py` 工位/人员利用率投影。
- 幂等：同幂等键同输入重放返回原结果；同键异输入 409 IDEMPOTENCY_CONFLICT。

## 8. M1 语义补充层（order_semantics.py）

外部 M1 对真实 XLSX 可能只返回「订单类文档但 0 行/缺订单号」（真实样本实测）。
本模块提供**不冒充外部 M1** 的确定性本地解析（表头/块事实/行级证据可复现，产出带
来源坐标与 SHA 的候选，标记 `m1.semantic-supplement.v1`），由 HTTP Adapter 附加
`semantic_supplement` 并强制 needs_review，**不覆盖**外部原始结果。历史五类解析缺口
（块标签别名/下邻取值越界（due_date 被"产品图片"污染）/占位"无"冒充编码/文本行当
明细/销售价装箱数未映射）已修复并有同构合成回归（真实样本不入库）。

## 9. 主链桥接（orchestration_bridge.py）

M0-M5 payload 装配 + 关键/非关键字段降级：从 M0 canonical 读已审批资源实体（设备/
工位/人员/日历）入 M5 snapshot；订单号/行 uom 进 order snapshot；routes 以
product_code 为 key 组装成 dict；M4/M5 契约枚举与日历接线；关键事实缺失降级为
BLOCKED_INPUT 或 defer（数据不全降级运行：M3 defer、M4/M5 降级、supplement
`{"degraded":true}` 可到 M5 feasible）。
