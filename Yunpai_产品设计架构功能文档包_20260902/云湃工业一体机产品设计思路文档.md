# 云湃工业一体机产品设计思路文档

> 版本：v0.1
> 更新日期：2026-09-02
> 文档性质：产品设计与产品叙事，不替代功能清单、接口契约、模块账本或运行验收报告
> 适用基线：`yunpai-0825-8fb686d5` 当前源码、项目总账及已确认的 M0/Orchestrator 设计决策

## 1. 先定义产品：它不是“多个模块的集合”

云湃工业一体机的产品定义是：

> 面向制造业的证据治理型全链路 Agent。它以一个统筹 Agent 作为唯一业务入口，以 M0 作为正式数据基础，把订单、工程、物料、采购、排程、成本和非标设计连接成可追踪、可恢复、可审计的业务执行链。

这一定义包含三个关键判断：

1. 产品的最小单位不是一个聊天回答，而是一项可以继续推进、暂停、恢复、验证和交付的业务任务。
2. 产品的核心资产不是某一个模型，而是“统一编排 + 结构化事实 + 证据链 + 可恢复执行”组成的闭环。
3. 产品的智能化不是让模型自由修改系统，而是让模型负责理解和规划，让确定性代码、数据约束和人工 Gate 共同控制执行风险。

因此，用户看到的不是 M1、M2、M3……八个彼此独立的入口，而是一个能理解制造业上下文并把任务交给正确模块的工作台。

## 2. 产品要解决的根问题

### 2.1 传统系统的断裂

制造业的真实工作通常从一份订单文件、一封邮件、一张图片或一句口头要求开始，随后需要多人在多个系统之间搬运信息：

```text
非结构化输入
    ↓ 人工识别、确认、抄录
订单/产品信息
    ↓ 工程人员查 BOM、SOP、物料编码
物料需求
    ↓ 采购人员拆分供应商、数量、交期
采购执行
    ↓ PMC 根据资源、工艺和优先级排程
生产计划
    ↓ 财务或管理人员汇总成本、风险和完成情况
结果分散在多个系统和聊天记录中
```

这种方式有五类根问题：

- 信息在模块之间重复录入，导致同一订单出现多个身份、多个版本和多个口径。
- 文件内容被识别成“答案”后就丢失了原始来源，后续无法说明字段从哪里来。
- 采购、排程、成本依赖前置事实，但前置事实发生变化时通常不会自动触发影响分析和重算。
- AI 可以给出建议，却无法把建议变成带状态、证据和后续动作的可交付任务。
- 操作经验往往停留在个人记忆里，系统既不会稳妥沉淀，也不应在无人知情时改变流程。

### 2.2 云湃要形成的改变

云湃把工作方式改成一条可观察的业务链：

```text
用户提出目标
    ↓
统筹 Agent 理解目标、识别输入和缺口
    ↓
生成可解释的执行计划
    ↓
调用正确模块并在模块间转换结构化数据
    ↓
每一步留下状态、事实、来源、证据和产物
    ↓
遇到异常才请人工决策，正常路径自动继续
    ↓
交付可下载、可追溯、可恢复的结果
    ↓
把经验和可固化操作先放入候选区，达标后再治理性进化
```

## 3. 产品面向谁，以及他们真正要完成什么

以下是产品设计阶段的目标用户画像，不代表已完成市场调研或商业定案。

| 角色 | 主要任务 | 他们关心的结果 | 云湃提供的产品价值 |
|---|---|---|---|
| 工厂/运营负责人 | 看订单能否交付、风险在哪里 | 全局状态和异常原因 | 一句话发起全链路任务，按订单/TaskID查看进度与证据 |
| 工程/BOM/SOP 人员 | 从图纸、表格和文档形成工程事实 | 结构化字段、版本和关联关系 | M1 解析，M0 统一实体、字段、来源和版本，M2 直接复用 |
| 采购人员 | 根据需求生成采购建议并推进执行 | 物料身份、数量、交期、状态 | M3 需求→M4 采购建议，异常时给出可审计的缺口和下一步 |
| PMC/计划人员 | 在资源约束下安排工序和交期 | 可执行计划、压力和影响范围 | M5 排程、计划版本、重算和订单级追踪 |
| 财务/审计人员 | 核对数量、金额和业务链路 | 口径一致、过程可回溯 | M6 成本上下文、事实账本、算法/输入/结果摘要 |
| 非标设计/工艺人员 | 将设计任务变成可交付制品 | 设计上下文、文件和人工介入点 | M8 作为子 Agent/设计工作台接入统筹任务 |
| 管理员/知识治理人员 | 控制权限、知识和流程变化 | 谁批准、依据是什么、能否回滚 | 证据系统、候选知识、工作流版本、暂停与回滚 |

产品设计的共同出发点是“用户交付一个目标”，而不是“用户必须知道该调用哪个模块”。

## 4. 产品的核心卖点

### 卖点一：一次对话，贯穿一条业务链

用户可以从“请根据这批订单和附件，给我形成物料需求、采购建议和可执行排程”开始。系统不要求用户先理解模块边界，而由统筹 Agent 把目标拆成步骤，沿 M1→M2→M3→M4→M5→M6 的链路推进；M8 作为设计型子 Agent 按需加入。

卖点不在于“能聊天”，而在于一次请求可以拥有同一个 `run_id`、`TaskID` 和 `trace_id`，从输入到交付保持连续。

### 卖点二：从“回答建议”变成“有证据的业务执行”

每个重要结果都应回答四个问题：

- 这一步做了什么？
- 使用了哪些输入和规则？
- 结果来自哪个来源、哪个版本、哪条证据？
- 下一步是自动继续、等待人工，还是失败关闭？

用户得到的不只是文本，还包括结构化结果、状态变化、审批记录、错误信息、下载制品和可继续运行的任务。

### 卖点三：M0 让数据先成为事实，再成为共享能力

M0 是所有模块的数据基础。它不替代 M2、M3、M4、M5、M6 的业务运行库，而是保存订单、产品、物料、BOM、文档、工程知识等正式实体的 canonical 事实、字段、关系、来源、证据和版本。

这样做的产品效果是：

- 同一物料可以通过别名、编码和来源被解析为同一身份。
- BOM、订单、库存、采购和排程之间可以建立逻辑关联，而不是依赖页面上的字符串拼接。
- 新数据进入系统时先识别类型、字段和关系，再决定是否成为正式事实。
- 事实变化可以触发影响分析、MRP/采购/排程新版本和历史复算。

### 卖点四：不确定时停下来问人，不靠猜

正常路径默认继续；只有匹配失败、置信不足、冲突、数据缺失或确实需要授权时，才打开统一 Gate。

Gate 必须显示：异常类型、证据摘要、受影响步骤、允许的动作、风险说明和审计结果。用户可以允许继续、拒绝终止，或暂停修改后再恢复同一个任务。缺少必要事实时系统硬暂停，不注入默认库存、不伪造数量、不用“看起来合理”的值代替缺口。

### 卖点五：把一次性操作变成可复用能力，但不让系统失控

系统会记录操作路径、重复步骤、错误和人工修正，但它们一开始都只是候选：

```text
观察到模式 → 进入缓存候选 → 多次独立出现/强证据 → 冲突与权限检查
    → 知识候选可晋升；操作模式只能形成工作流候选
    → 人工确认后生成新版本 → 可监控、可暂停、可回滚
```

经验自进化和操作自进化因此都有边界：知识可以在证据门槛后进入主动召回；编排不能由 Agent 静默改写，必须经过人工弹窗确认。

### 卖点六：进度、结果和责任都能追溯

以订单或 TaskID 为中心，用户可以看到输入、每个模块步骤、数据桥接、人工决策、输出制品、错误和恢复记录。管理者可以追踪“为什么得到这个结果”，开发者可以定位“在哪一步断了”，审计人员可以确认“谁在什么证据下批准了什么”。

## 5. 产品设计的五条原则

### 5.1 一个根入口，一个根执行者

外部业务任务优先进入统筹 Agent。模块保持独立故障域和业务所有权，但不直接互相拼接成不可见的旁路链路。统筹 Agent 负责理解、计划、调度、桥接、状态、Gate 和恢复。

### 5.2 M0 管正式事实，模块管运行事实

M0 负责跨模块共享的 canonical 实体、字段、关系、版本和来源；M1-M8 保留各自运行过程、算法中间态和领域专属结果。任何新数据先判断是正式业务事实、运行结果、证据、候选知识还是原始情景记忆，避免把不同层级混为一谈。

### 5.3 模型做理解与规划，代码做约束与执行

模型适合处理自然语言意图、文件语义、步骤选择、候选比较和结果解释；确定性代码负责身份、权限、字段校验、数量/金额守恒、幂等、状态机、版本和副作用门禁。高风险写入不由模型单独决定。

### 5.4 默认自动继续，异常统一 Gate

用户不应为每一步点击确认，也不应在不同模块学习不同弹窗。系统把正常流程做短，把异常信息做全；Gate 的动作要绑定当前证据摘要和同一 `run_id`，避免“看过旧页面后误放行”。

### 5.5 先缓存、再证据、后晋升

经验、错误、输入数据理解、映射候选和操作模式首次出现都进入持久化候选区。普通候选至少需要 3 个独立任务或输入，或达到约定的强证据条件，并通过冲突、权限、版本和安全检查，才有资格晋升。重试、同源副本和上游转抄不能伪造独立证据。

## 6. 用户使用逻辑：从目标到交付的六段闭环

产品的主交互模型是：

```text
理解 Understand
    → 计划 Plan
    → 执行 Execute
    → 校验 Verify
    → 交付 Deliver
    → 沉淀 Learn
```

### 6.1 理解：用户只需说明目标

入口可以是中文自然语言、上传文件、已有订单号、TaskID 或模块工作台中的结构化表单。系统先识别：任务类型、主体对象、时间/数量约束、附件类型、已有身份、所需模块和缺失信息。

对于文件，M1 负责解析和抽取；data-adapter 负责格式/字段适配；M0 负责候选实体、字段、来源和关系的统一表达。解析结果不会直接覆盖正式事实。

### 6.2 计划：系统把目标翻译成可见步骤

统筹 Agent 生成步骤计划并说明依赖关系，例如：

```text
读取订单附件
  → 解析产品、数量、交期
  → 解析/生成 BOM 与 SOP
  → 发布 BOM 到 M0
  → 计算物料需求
  → 生成采购建议
  → 检查物料准备度
  → 生成采购单/更新采购状态
  → 根据资源和优先级排程
  → 保存全链路追踪与交付制品
```

用户可以在计划阶段看到预计产物、可能需要的权限和会触发副作用的步骤；不需要了解内部 HTTP 工具名。

### 6.3 执行：由编排层驱动模块协作

编排层使用工具注册表和 JSON Schema 构造调用，解析步骤引用，完成文件 base64→multipart、M2→M3、M3→M4、M4→M5、M5→M6 等桥接；M8 通过 Agent 调用、轮询中间态和介入决策参与。

执行过程中每一步至少产生：状态、输入摘要、输出摘要、源引用、证据引用、版本信息、耗时和错误/重试信息。模块不需要知道下游页面如何展示，但必须遵守输入输出合同。

### 6.4 校验：先确定性检查，再让人决策

系统在关键边界做身份、字段、权限、数量、金额、状态、幂等和后置条件检查。对库存、采购、排程、成本等结果，还要做事实账本对账和不变量门禁。

异常时打开统一 Gate：

| Gate 动作 | 产品语义 | 结果 |
|---|---|---|
| 允许继续 | 用户认可当前证据下的有限动作 | 继续同一 run/TaskID，不跳过审计 |
| 拒绝 | 用户否定当前方案或授权 | 终止下游，保存 `OPERATOR_REJECTED` 等审计状态 |
| 暂停修改 | 用户需要补充或修正输入 | 保留可恢复状态，只开放必要编辑面板 |

### 6.5 交付：交付“结果包”而不是一句话

一次任务的交付应包含：结构化数据、业务状态、下载文件或报表、证据与来源、人工决策、未解决问题、下一步入口和可恢复的任务链接。用户可以按订单、物料、采购单、排程、成本或 TaskID 反向追踪。

### 6.6 沉淀：把使用反馈变成受治理的候选

任务完成、人工纠正、重复失败、字段映射和高频操作会产生候选记录。候选保留原始输入哈希、精确定位、来源、关联任务、观察次数、冲突和状态；只有满足门禁的知识才进入主动召回，只有人工批准的操作候选才会形成新工作流版本。

## 7. 端到端功能路径

### 路径 A：订单到计划的主路径

```text
用户：上传订单/图纸并提出交付目标
  ↓
M1：识别文档、表格、图片，抽取订单和产品字段
  ↓
M0：解析结果进入候选区，匹配已有实体/字段/关系
  ↓
Orchestrator：生成并展示业务 StateGraph 计划
  ↓
M2：解析或生成 BOM/SOP，返回结构化 BOM
  ↓
M0：发布经过审核的 BOM 版本和来源
  ↓
M3：按 M0 工程事实计算 MRP、短缺、采购建议
  ↓
M4：创建/更新采购任务并追踪状态
  ↓
M5：读取物料与订单上下文，生成资源约束下的排程
  ↓
M6：接收排程和执行事实，形成成本上下文
  ↓
Orchestrator：写入 TaskID/trace、交付结果，提供下载与恢复
```

用户体验上，这是一项任务；系统内部才展开为多个模块步骤。任一中间步骤暂停后，用户回到同一任务即可继续，不需要从头提交。

### 路径 B：查询和追溯

用户可以问“订单 SO-xxx 现在到哪一步”“这个物料为什么短缺”“这个成本差异来自什么消耗”。Orchestrator 先识别查询主体，再从 M0、业务投影、TaskID/trace 和模块结果中拼接答案；结果必须显示来源和时间版本，不以聊天上下文代替事实查询。

### 路径 C：新数据入库

```text
文件/表格/API 输入
  → 类型识别与解析
  → 字段/别名/实体匹配
  → 候选结构与逻辑关联
  → 缺失/冲突 Gate
  → 人工审核或自动通过确定性校验
  → M0 正式版本 + SourceRef/EvidenceRef
  → 下游模块可读取
```

新数据的“拓展入库”不是直接 INSERT 一张孤立表，而是先回答：数据属于什么类型、对应哪个实体、字段是什么、与哪些已有事实有关、来源是否可定位、是否会产生新版本或影响重算。

### 路径 D：经验自进化

经验候选包括：某类输入的稳定字段含义、某个错误的复发条件、某种人工纠正后的正确映射、某个任务的有效处理顺序。候选进入缓存后经过独立性计数、证据核验、冲突检查、权限检查和版本检查，成为 active knowledge；Planner 只注入 active knowledge，不直接读取未经门禁的候选和原始情景记忆。

### 路径 E：操作自进化

系统发现“相同条件下用户总是重复执行 A→B→C”，可以提出工作流修改建议。建议必须说明触发条件、拟合并步骤、减少的人工动作、影响范围、回退方式和示例证据。人工批准后才生成不可变的新编排版本；上线后可暂停或回滚，Agent 不能自行改源码、权限、工具白名单或 M0 物理 Schema。

## 8. 产品界面与信息分层

### 8.1 统一工作台

这是大多数用户的入口，承担自然语言输入、文件上传、计划预览、实时进度、Gate 决策、结果摘要和继续运行。工作台应该让用户始终知道三件事：任务正在做什么、为什么停下、下一步能做什么。

### 8.2 任务中心

按 `run_id`、TaskID、订单、负责人、状态和时间筛选任务。状态至少区分运行中、等待人工、数据缺失、已完成、已拒绝、失败和可恢复；任务详情展示步骤图、日志摘要、证据和制品。

### 8.3 结构化数据与证据审阅

用于查看 M0 实体、字段、别名、关系、版本、来源和证据。用户可以定位到原文件页码/行号/段落，比较新旧版本，确认候选映射，处理冲突和失效来源。

### 8.4 业务追踪驾驶舱

围绕订单或物料查看订单→BOM→MRP→采购→排程→成本的链路，展示短缺、延误、资源压力、数量守恒和影响分析。驾驶舱的主语是业务对象，不是微服务。

### 8.5 模块工作台

工程、采购、排程和设计人员仍可进入 M2、M4、M5、M8 的领域工作台，但领域页面产生的任务和结果应能回到统一 TaskID/trace；模块工作台是专业操作面，不是另一套事实源。

### 8.6 知识与进化治理台（规划）

用于查看候选、证据、重复计数、冲突、晋升、暂停、删除、工作流提案、批准人、版本、回滚和基本指标。它是治理入口，不是让用户手工维护一张“万能知识表”。

## 9. 数据与证据如何支撑产品体验

### 9.1 数据分层

| 层级 | 含义 | 是否可直接驱动业务 |
|---|---|---|
| 原始输入 | 文件、表格、API 请求、人工填写 | 否，需解析和校验 |
| 候选结构 | 实体/字段/关系/映射的待确认表达 | 否，需 Gate 或确定性通过 |
| M0 canonical 事实 | 正式实体、字段、关系、版本和来源 | 是，按权限和版本读取 |
| 模块运行事实 | MRP、采购、排程、成本等领域结果 | 是，但由模块合同和编排状态约束 |
| 证据与审计 | SourceRef、EvidenceRef、决策和操作记录 | 作为可追溯依据，不替代业务事实 |
| 知识候选/active knowledge | 经验、错误规律、输入理解、操作模式 | 候选不可直接驱动；active knowledge 可辅助规划 |

### 9.2 结构化数据的最低表达

一个可用的数据对象至少需要：稳定身份、类型、字段值、字段来源、版本、生效状态、与其他对象的关系以及证据定位。当前源码已具备部分订单、BOM、物料、库存、事实和版本结构；完整的 Schema Registry、字段词典、关系定义、映射候选和 SourceRef v2 仍是 M0 改造重点。

### 9.3 证据不是装饰，而是决策输入

证据系统用于：确认抽取值、解释模块结果、支持 Gate、判断知识晋升、追踪来源失效和支撑回滚。证据应保留原文引用、哈希、来源类型、定位、采集时间和关联任务；只存一句模型总结不足以支撑审计和进化。

## 10. 当前实现与产品目标的边界

产品设计必须诚实区分“已可使用的骨架”和“需要开发的目标能力”。

| 产品能力 | 当前状态 | 产品含义 |
|---|---|---|
| 统筹 Agent 单入口、LLM Planner、工具注册和 ReAct/业务 StateGraph | 已有源码基础 | 已形成产品的执行中枢，但仍需按目标环境完成发布 Gate |
| M1→M2→M3→M4→M5→M6 数据链路、桥接、TaskID/trace、恢复 | 已有源码/静态与部分隔离证据 | 可作为产品主路径设计基线，不等于所有模块生产可用 |
| M0 PostgreSQL canonical、统一投影、版本/事实/来源 | 已有基础，字段/关系 Registry 仍有缺口 | 能支撑统一事实方向，需继续补齐数据治理能力 |
| M1 解析、M2 BOM/SOP、M3 MRP、M4 采购、M5 排程、M6 成本、M8 设计接入 | 模块能力不均衡 | 产品展示应根据真实模块状态标注，不把声明当成完整上线 |
| 默认继续、异常 Gate、允许/拒绝/暂停恢复 | 已形成编排和前端设计基线 | 是产品核心体验，需要持续补齐边界用例 |
| 经验候选缓存、三次独立门禁、证据晋升、主动知识召回 | 已确认方案，运行时待开发 | 是 P1 受治理知识能力，不是当前自动学习事实 |
| 操作模式发现、工作流提案、人工批准、新版本、暂停/回滚 | 已确认方案，运行时待开发 | 是 P2 操作自进化能力，不是 Agent 自行改流程 |
| M7 法务 | 当前未交付 | 不能在产品宣传或验收中当作已接入模块 |

当前 `module_decls` 静态声明合计为 129 个工具/声明，其中 M7 为 0；项目总账中的“业务模块 79 个”采用的是另一种历史计数口径。产品文档不以工具数量作为卖点，工具数量仅用于开发和范围核对。

## 11. 产品范围与明确不做什么

云湃不是：

- 一个只会回答问题的通用聊天机器人；
- 把所有 ERP/PLM/MES 功能一次性替代掉的“大而全系统”；
- 让模型绕过权限、状态机或事实校验的自动化脚本；
- 未经人工批准就自动改源码、改工具白名单、改权限或改 M0 物理 Schema 的自编程系统；
- 首期就建设独立测评器、复杂评测平台、伪造数据识别、存储额度/计费、复杂 shadow/canary 的研究平台。

这些边界让首版产品把资源集中在“真实业务链跑通、事实可追溯、异常可控、经验可沉淀”四件事上。

## 12. 版本演进思路

### P0：可执行的统一业务中枢

目标是让用户从统一入口完成一条真实业务链：任务创建、计划、模块调用、数据桥接、M0 事实、TaskID/trace、Gate、结果交付和恢复。P0 的核心不是自进化，而是建立可信的执行闭环。

### P1：受治理的数据理解与知识沉淀

补齐 M0 Schema Registry、字段/关系/别名、数据 Profile、SourceRef/EvidenceRef、候选缓存、独立任务计数、强证据门禁、候选召回、纠错/暂停/删除和基础指标。P1 让系统能“记住什么”，但不让它无条件相信什么。

### P2：可批准的操作自进化

增加操作模式候选、工作流提案、影响说明、人工弹窗、不可变版本、启用、暂停、回滚和版本审计。P2 让高频繁琐操作可以固化，同时保持人的最终控制权。

### P3：模块和生态完善

补齐 M7、M5 正式资源、M6/M8 产品化工作台、真实外部系统适配器和更多领域制品。P3 扩大覆盖面，但不改变“一个根入口、一个事实基础、证据门控”的产品骨架。

## 13. 产品成功如何判断

以下是设计指标，不是当前已达成的数值承诺：

1. 有证据的任务完成率：任务完成且输出、来源、状态和审计完整的比例。
2. 正常路径自动继续率：无需人工介入即可完成的步骤比例，同时单独统计异常路径的正确拦截率。
3. 从输入到交付的时间：按任务类型比较文件进入到可用制品的耗时。
4. 结构化抽取纠正率：M1/M0 候选需要人工修正的字段比例及其下降趋势。
5. M0 canonical 覆盖率：跨模块引用的订单、产品、物料、BOM 等是否有稳定身份和来源。
6. 追踪完整率：从输入到模块步骤、Gate、输出和版本能否用同一 TaskID/trace 回放。
7. 知识候选有效率：晋升后的知识被成功复用且未造成错误的比例。
8. 工作流提案接受/回滚率：被批准的操作候选是否真正减少重复操作，以及出现问题时是否能快速回滚。
9. Fail-closed 正确率：在数据缺失、冲突、权限不足时是否正确暂停，而不是产生看似完整的伪结果。

指标应服务于产品决策，不应反过来驱动系统制造证据或追求没有业务价值的自动化率。

## 14. 仍需产品确认的设计决策

以下项目已经有默认方向，但仍需在实施前逐项定稿：

- “强证据”由哪些证据类型组合构成，是否允许不同来源类型加权；
- 候选、证据、情景记忆和 active knowledge 的具体保留期；
- 知识晋升人与工作流版本批准人是否必须分离；
- 不同模块和租户的工具白名单边界；
- 哪些知识范围可以自动进入 Planner，哪些必须每次人工选择；
- 工作流新版本的启用范围、观察期和回滚责任人；
- 生产身份模式、Job/Memory 租户隔离和 Alembic 前置迁移的落地顺序。

这些决策会影响权限、数据结构和发布流程，不能由 Agent 在运行时自行推断。

## 15. 设计结论

云湃的产品价值可以浓缩为一句话：

> 把制造业中分散、依赖经验、难以追溯的多系统工作，变成一项由统筹 Agent 驱动、以 M0 事实为基础、由证据和人工 Gate 约束、能够持续沉淀但不会失控自改的可恢复业务任务。

它的竞争力不是“模块数量多”，而是把以下关系做成产品体验：

```text
自然语言目标
  + 结构化数据
  + 模块能力
  + 证据与来源
  + 人工决策
  + 可恢复执行
  + 受治理的知识/流程沉淀
  = 面向制造业的可信业务执行中枢
```
