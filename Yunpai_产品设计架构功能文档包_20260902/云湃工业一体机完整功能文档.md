> 版本：v1.0（2026-09-02）  
> 适用源码：`yunpai-0825-8fb686d5`  
> 目的：把当前源码/工具声明中的具体功能、输入输出、数据落点、依赖、状态和缺口整理成单一功能参考。  
> 状态定义：`源码存在` 不等于生产可用；`部分闭环` 表示有代码但仍依赖人工、外部服务或未完成治理；`规划待开发` 表示已确认需求但当前源码缺少闭环；`未交付` 表示没有对应代码。

## 2. 功能状态和统一约束

### 2.1 状态

| 状态 | 判定 |
|---|---|
| 源码存在 | 当前源代码或工具声明能找到实现/注册，不代表依赖服务已运行 |
| 局部可用 | 有真实逻辑，但受数据、权限、模型、外部系统或人工 Gate 限制 |
| 规划待开发 | 已写入确认的产品规格，但缺少持久化、API、Worker、UI 或闭环代码 |
| 遗留兼容 | 为旧调用保留，不应作为新业务链路的默认入口 |
| 阻断/缺口 | 当前条件不足时必须失败关闭、暂停或等待补充 |

### 2.2 全局约束

- M0 保存正式实体、字段、关系、版本、来源和证据；模块和 Orchestrator 不得建立第二套 M0 业务事实。
- 模块之间不直接互调，跨模块交接由 Orchestrator bridge 完成。
- 需要副作用的动作必须经过权限、TaskID、幂等和人工 Gate。
- LLM 负责理解、分类、检索、草拟和建议；确定性代码负责身份、权限、Schema、数量/金额、幂等、后置条件、回滚和执行证据。
- 缺少真实事实、授权或依赖时返回 `needs_input`、`needs_approval`、`blocked` 或 `data_incomplete`，不能用默认数据补齐。
- 普通已审核订单、BOM、库存等业务事实不适用三次重复门禁；三次独立出现只用于系统学习的经验、错误、映射、纠正和操作模式。

### 4.4 M0 目标结构和缺口

当前正式结构：`core.entities`、`core.entity_versions`、`core.entity_aliases`、`core.entity_relations`、`knowledge.source_assets`、`knowledge.source_occurrences`、`knowledge.evidence_anchors`、`knowledge.field_claims`、`knowledge.relationship_claims`、`staging.structured_records`、`staging.field_candidates`、`staging.identity_candidates`、`staging.relationship_candidates`、`audit.audit_events`。

目标扩展：

- `entity_type_definitions`：租户、实体类型、定义版本、JSON Schema、业务键规则、生命周期和审批人。
- `field_definitions`：字段路径、数据类型、单位维度、规范单位、必填、枚举、声明式校验、敏感级别和版本。
- `field_aliases`：来源系统外部字段、语言、目标规范字段和状态。
- `relation_type_definitions`：source/target 类型、方向、多对多、版本端点和证据要求。
- `schema_proposals`、`field_mapping_candidates`：未知结构、字段映射、字段变更和新关系候选。
- `schema_change_receipts`：提案前后版本、批准摘要、执行主体和结果，只追加。

M0 缺口：动态 Registry、字段词典、关系定义、M0 v2 通用实体、SourceRef/EvidenceRef 分离、跨模块正式客户端、来源失效级联和学习候选与 M0 的边界实现尚需开发。

### 5.2 输出与数据落点

`m1.document.v2` 包含：原文件名、展示名、SHA-256、MIME、归档路径、Sheet/页码、文档类型/子类型、订单头、明细行、规格属性、汇总、字段证据、字段元数据、校验问题、审核状态和兼容载荷。

M1 本地表：`tasks`、`task_summary_rows`、`document_records`、`order_line_records`、`field_index_records`、`outbox_worker_tenants`。生产职责是 parser-only，候选交给 M0；M1 不拥有 active 产品、订单、BOM、Wiki、Graph 或统一知识搜索。

### 5.3 M1 缺口

- 5 个遗留知识工具和 13 个知识 API 仍可能造成双事实源。
- `m1.document.v2` 同时承担解析结果、订单结构和旧兼容载荷，需要 `m1.candidate.v1` 外封套。
- M1 技术审核与 M0 业务审核尚未完全分离。
- M0 接收确认、revision、保留期和临时文件清理契约不完整。
- PPTX/HTML 路由存在但完整适配/验收不清楚；DWG 依赖外部 DXF 转换器。
- 解析器、模型、GPU 和外部转换器必须建立格式级 readiness；当前没有跨任务纠错到候选/证据/发布的学习闭环。

`run_mrp_procurement_plan`、`list_m3_orders`、`get_m3_order`、`get_m3_procurement_plan`、`get_persisted_m3_plan`、`get_material_readiness`、`get_pr_po_drafts`、`get_m3_approval_tasks`、`approve_m3_task`、`reject_m3_task`、`request_change_m3_task`、`approve_to_send_m3_task`、`get_m3_m4_handoffs`、`export_m3_procurement_suggestions` 仅为旧调用兼容。采购单、供应商消息和采购执行职责已迁移到 M4。

M3 保存库存、MRP、分配和齐套运行事实；产品/BOM/工程参考读 M0。缺 approved/released BOM、交期或匹配事实时失败关闭，不把草稿 BOM 直接送入采购。

## 8. M4 采购追踪功能

### 8.1 采购建议、采购单和审批

`import_m4_purchase_suggestions`（旧 CSV，本地兼容）、`import_m4_purchase_suggestions_json`（正式 Orchestrator JSON）、`list_m4_purchase_suggestions`、`generate_m4_purchase_orders`、`list_m4_purchase_orders`、`get_m4_purchase_order`。

具体规则：导入建议按 tenant/site/TaskID/版本归属；同一完整建议集合重放返回原采购单，范围/来源/TaskID 不一致或部分复用返回冲突。采购单状态为 draft/request_changes → pending_review → approved_for_message；批准只生成供应商邮件草稿，不表示已经发送、到货或形成库存事实。

### 8.2 采购单审核和消息

`submit_m4_purchase_order_review`、`approve_m4_purchase_order`、`request_changes_m4_purchase_order`、`generate_m4_purchase_inquiry_message`、`send_m4_purchase_order`（旧本地兼容）。

所有受控写操作绑定根 TaskID 和当前 revision/checksum；过期写入返回 409；消息保存收件人、附件和人工核对快照，审批前不得进入外部投递。

### 8.3 供应商和回复

`list_m4_suppliers`、`create_m4_supplier`、`update_m4_supplier` 管理供应商主数据；`create_m4_supplier_reply` 保存回复原文；`parse_m4_supplier_reply` 提取交期、价格、币种、税含标记和异常；低置信度进入 `need_human_review`；`confirm_m4_supplier_reply` 人工确认或修正后才形成正式承诺。

### 8.4 追踪、预警和 M5 供应投影

`list_m4_tracking`、`scan_m4_purchase_alerts`、`list_m4_purchase_alerts`、`generate_m4_urge_message` 管理采购进度、超期/临期/供应商异常及催单草稿。`query_m4_material_supply_snapshot`、`list_m4_material_supply_events`、`get_m4_material_supply_snapshot`、`confirm_m4_supplier_fact` 为 M5 提供带 tenant/site、版本和 checksum 的供应投影。无权威收货事实时 `received/open/ETA/confidence` 需保持 null，不能释放排程。`receive_m4_schedule_impact_proposal` 只受理 M5 的计划影响建议，不能自动改采购。

## 11. M8 非标自动化 ID 设计功能

`run_id_design` 是一个灰盒子子 Agent：

```text
产品需求文本
  → intake
  → id_design
  → validate
  → quality_evaluate
  → clarify / image2
  → human_gate
  → persist
```

输入为产品/非标设备设计需求文本；输出为 Project File(JSON)、设计报告(Markdown)、质量评审（评分/覆盖度/发现）、可选产品渲染图和 BOM 草稿。Orchestrator 负责触发、轮询和介入决策；M8 自己保存设计过程和生成物。M0 应提供设计项目、图纸版本和工程变更基线，M8 不成为工程主数据事实源。当前工作台和真实 LLM/checkpointer 接线仍需产品化/环境验收。

## 13. 知识库、证据和简单自进化功能（目标）

### 13.1 经验自进化

1. 一次 Job/Chat/Business Flow 完成后记录任务、工具步骤、结果、错误、人工纠正引用。
2. Observation Hook 将经验、错误、Data Profile、字段映射和操作模式写入 PostgreSQL 候选区。
3. 用结构指纹聚合；同一 Trace 重试、同哈希副本、同一业务记录重复拉取不计为独立证据。
4. 普通候选达到 3 个独立任务/输入，或获得 M0 正式版本、模块正式 Schema/错误码、人工纠正后成功结果之一，才进入晋升检查。
5. 检查范围、权限、来源可访问、反例、Schema 版本和敏感内容；通过后以 user/project/tenant 最小范围发布。
6. 后续任务检索时，Planner 获得知识正文、适用条件和证据引用，并记录实际使用和结果。
7. 出现反例或来源失效时暂停知识；纠正创建新版本，不覆盖历史。

### 13.2 输入数据理解

Data Profile 至少保存：数据载体、字段名和路径、物理类型、语义类型、单位、值域、空值、主键/引用、质量问题、M0 entity/field/relation/alias 匹配结果和版本。

- 已知结构：保存 M0 ID 和 definition_version。
- 未知结构：只生成字段映射候选或 Schema 提案。
- 冲突别名、未知字段和关系端点必须进入候选区，不能由 Agent 直接改变 M0。

### 13.3 操作自进化

1. 从成功 Trace 中提取连续工具步骤和人工操作。
2. 同一模式达到 3 个独立任务后生成“可固化操作”待办。
3. 生成受限工作流 JSON，展示当前步骤、建议步骤、触发条件、输入输出、权限和副作用。
4. 只做基础校验：JSON Schema、工具存在、参数类型、权限、循环、幂等键和人工 Gate。
5. 弹窗提供批准、修改后批准、拒绝、稍后处理。
6. 批准时绑定候选版本、证据摘要和审批人，创建不可变工作流新版本。
7. 新版本出现异常时人工暂停或回滚到上一版本。

### 13.4 目标核心表

`orch_knowledge.sources`、`candidates`、`candidate_sources`、`knowledge_items`、`knowledge_actions`、`knowledge_usage`、`workflow_proposals`、`workflow_versions`。

候选字段重点：`fingerprint`、`content`、`applicability`、`status`、`independent_occurrence_count`、`support_count`、`contradiction_count`、`last_error`、来源和版本。大文件只保存稳定位置、哈希和定位，不复制进表。

### 13.5 当前缺口

| 功能 | 当前状态 |
|---|---|
| 工作/会话/情景/语义记忆 | 源码存在，但保存的是作业历史，不是结构化经验 |
| 候选缓存和状态机 | 缺失 |
| Claim-Evidence/SourceRef | 缺失，Trace/日志尚未统一成证据关系 |
| K0–K4 分层知识库 | 缺失 |
| 失败根因、纠正、验证和反例 | 部分存在，未形成闭环 |
| 召回正文注入 Planner | 缺失；当前主要传命中数量/上下文摘要 |
| Data Profile 和 M0 映射学习 | 分散存在，缺统一模型和版本复用 |
| Trace 操作模式挖掘 | 缺失 |
| 工作流 DSL、diff、风险校验 | 缺失 |
| 自进化专用人工弹窗 | 只能复用普通业务 Gate，专用功能缺失 |
| 工作流 Registry、active/suspend/rollback | 缺失 |

明确非目标：不建设独立测评器、黄金样本平台、伪造数据/刷证据识别、存储额度/计费、复杂 shadow/canary；不允许 Agent 自动修改源码、系统 Prompt、权限策略或 M0 物理 Schema。

## 15. 功能缺口优先级

### P0：不先解决会污染或阻断后续能力

1. 生产身份模式、principal、真实 tenant/data_scope。
2. Job、Memory、Redis、Chroma 和模块数据库隔离。
3. API 启动 DDL 迁移到 Alembic/有序迁移。
4. 原始情景记忆与正式知识分离。
5. M0 v2 Registry、字段词典、关系定义和 SourceRef/EvidenceRef。
6. Planner 接收 active 知识正文、适用条件和证据，并记录 usage。
7. M0/M1 业务审核与技术审核边界、M0 接收 ack/revision/保留期。

### P1：形成可使用的知识和数据理解闭环

1. `orch_knowledge` 八张表、候选状态机和独立出现计数。
2. Claim-Evidence、来源失效级联、纠错/暂停/恢复/删除。
3. Data Profile、字段映射候选、M0 Schema 提案和人工批准。
4. 权限过滤、精确/结构化/全文/向量分级检索。
5. 知识使用效果、反例和基础积压指标。

### P2：操作自进化

1. Trace 子序列和人工操作模式聚合。
2. 受限工作流 JSON Schema、diff、风险和副作用检查。
3. 专用审批弹窗、候选版本、启用、暂停和一键回滚。
4. 工作流版本与 Orchestrator 动态路由的绑定。

### 模块和部署缺口

- M7 法务代码未交付。
- M5 正式生产资源、真实工艺/班次/产能数据仍需 Gate。
- M6/M8 在线接入和前端工作台需要按目标环境验收。
- M5 外部受控 fixture、M8 外部 Excel 和陈旧测试断言仍有缺口。
- DWG 转换器、MinerU/Instructor/VLM/GPU、ERP/WMS/MES/PLM 等依赖需独立 readiness。

## 16. 验收建议

任何“已实现”功能最终都需要三类证据：

1. 模拟人工点击或 API 操作序列。
2. 真实合理、符合业务口径的输入和输出。
3. 数据库状态、版本、TaskID、Outbox、证据和回滚结果符合预期。

本次文档整理只做静态源码/声明/台账复核，未启动业务服务、未修改数据库、未进行生产部署或端到端功能验收。
