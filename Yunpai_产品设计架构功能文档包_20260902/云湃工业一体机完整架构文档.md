# 云湃工业一体机完整架构文档

> 版本：v1.0（2026-09-02）  
> 适用源码：`yunpai-0825-8fb686d5`  
> 文档性质：架构与开发交接基线；依据当前源码、`module_decls` 静态工具声明、项目台账和既有设计文档整理。  
> 重要口径：本文把“源码存在”“局部测试通过”“规划待开发”“未验证”分开描述，不把静态盘点写成生产验收结论。

## 1. 架构结论

云湃工业一体机采用“模块化服务边界 + M0 统一数据面 + 服务端 LangGraph 统筹”的结构：

1. `Orchestrator` 是唯一跨模块编排入口，负责理解请求、创建任务、选择工具/子 Agent、转换上下游载荷、处理状态和人工 Gate、汇总结果及追踪。
2. M0 是正式实体、字段、关系、版本、来源和证据的权威基础。业务模块不能直连 M0 数据库，必须使用 M0 API 或注册工具。
3. M1–M6 主要作为工具服务，M8 作为独立子 Agent 接入；模块之间不恢复直接业务 handoff。
4. 模块自己的运行事实仍归模块保存：例如 M3 的库存/MRP、M4 的采购执行、M5 的排程/执行、M6 的成本计算、M8 的设计过程。
5. 统筹 Agent 的经验、错误、Data Profile、操作模式和工作流版本属于 Orchestrator，不复制 M0 正式业务事实。
6. 知识库与证据系统、自进化闭环是已经确认的产品目标，但当前源码只具备记忆、Trace、业务 Gate 等基础，候选缓存、证据晋升、工作流 Registry 等仍待开发。

## 2. 总体拓扑

```text
用户 / 前端工作台 / 外部 API / 文件上传
                 │
                 ▼
      Identity BFF / API Gateway
      tenant · data_scope · RBAC · TaskID
                 │
                 ▼
      Orchestrator 根执行者
      ├─ Chat/SSE 与 /invoke
      ├─ ReAct：plan → act → observe → judge
      ├─ 固定业务 StateGraph：M1 → M2 → M3 → M4 → M5 → M6
      ├─ M8 子 Agent：触发、轮询、人工介入、结果回收
      ├─ 工具注册/Schema 校验/HTTP 调用/文件 multipart
      ├─ 5 类跨模块数据桥接
      ├─ Job/TaskID/Trace/幂等/暂停/恢复/审计
      └─ L1/L2 Redis + L3 PostgreSQL + L4 Chroma 记忆
                 │
       ┌─────────┼─────────────────────────────────────┐
       ▼         ▼                  ▼                   ▼
      M0       M1–M6 工具面        M8 子 Agent         外部业务系统
   canonical  解析/BOM/MRP/采购/    非标 ID 设计       ERP/WMS/MES/PLM/文件
   数据基础   PMC/成本             Project File
```

### 2.1 分层职责

| 层 | 组件 | 责任 | 不应承担的责任 |
|---|---|---|---|
| 接入层 | Frontend、Identity BFF、API Gateway | 身份、请求接收、文件上传、审批界面、结果展示 | 直接串联业务模块、直接写模块数据库 |
| 统筹层 | Orchestrator | 意图理解、计划、工具选择、调用、状态、Gate、追踪、聚合 | 复制 M0 canonical 事实、绕过审批执行副作用 |
| 权威数据层 | M0 PostgreSQL | 实体、字段、关系、版本、来源、证据、active 工程事实 | 保存对话记忆、模块运行结果、工作流版本 |
| 工具服务层 | M1–M6 | 模块专有计算、解析和业务运行事实 | 形成跨模块第二事实源、绕过 Orchestrator 直接交接 |
| 子 Agent 层 | M8 | ID 设计拆解、方案验证、质量评审、生成物 | 代替 M0 管理工程主数据 |
| 记忆/演进层 | Redis、Orch PostgreSQL、Chroma、规划中的 `orch_knowledge` | 短期状态、历史记忆、候选知识、工作流版本 | 未经门禁把候选当 active 知识 |

## 3. Orchestrator 运行架构

### 3.1 请求入口与任务上下文

当前源码入口包括：

- `/health`：健康检查。
- `/invoke`：一次性提交自然语言任务，生成 Job 并执行 ReAct Agent。
- `/chat/stream`：流式聊天，返回 LLM 文本、工具步骤、结构化 DataRef 和结果链接。
- `/business-flows`：创建受治理业务流。
- `/business-flows/{run_id}/resume`：仅对可恢复的人工输入或 blocked 状态继续运行同一个 run。
- `/jobs/{job_id}`、`/jobs`：作业状态和结果。
- `/tasks`、`/tasks/{task_id}`：TaskID 任务查看和状态操作。
- `/chat/conversations*`：会话创建、消息读取、更新和删除。

一次请求的逻辑上下文至少包括：

```text
principal / tenant_id / data_scope_id
task_id 或 tracking_task_id
job_id / run_id / trace_id
conversation_id（聊天请求）
idempotency_key（有副作用的写操作）
selected_tools / input files / current workflow version
```

生产身份、租户和数据范围是当前开发前置问题；不能用 `tracking_default_tenant` 代替真实业务租户归属。

### 3.2 动态 ReAct 循环

```text
接收自然语言
  ↓
LLM Planner：意图理解、工具选择、payload 构造
  ↓
Registry：读取 tool.json，做全局唯一性和 JSON Schema 校验
  ↓
策略层：身份、权限、幂等、人工 Gate、文件/敏感字段检查
  ↓
执行：M0–M6 HTTP 工具 / M8 子 Agent
  ↓
结果 Envelope：成功、需要输入、需要审批、阻断、部分成功、失败、取消
  ↓
Observe：保存步骤输入摘要、输出、错误、trace 和数据引用
  ↓
Judge：继续规划、结束、请求人工、重试或可恢复失败
  ↓
Summary/SSE：自然语言总结 + 结构化结果 + 可下载制品链接
```

当前实现可见的具体能力：

- `LLMPlanner.plan()` 根据工具 Schema 生成 action JSON。
- `_resolve_step_refs()` 解析 `${steps.xxx.result}` 等前置步骤引用。
- `_adapt_m2_to_m3()` 将 M2 `standard_bom` 适配为 M3 `order+bom.lines`。
- `_adapt_m4_to_m5()` 将 M4 供应追踪和 M3 订单组合成 M5 排程请求。
- `_adapt_m5_to_m6()` 将 M5 排程指标转换成 M6 成本上下文。
- `_file_uploads` 将 base64 文件字段转换为 multipart 上传。
- `_act_agent()` 触发 M8、轮询中间态，并根据需要进入人工介入。
- `sanitize_model_output()`、敏感字段识别和安全摘要控制模型输入/输出。

当前缺口：记忆召回可以发生，但 active 知识正文和证据没有完整进入 Planner；候选知识、使用效果、工作流版本还没有正式 Registry。

### 3.3 固定业务 StateGraph

主流程节点：

```text
START
  ↓
intake
  ├─（显式压测/模拟条件）→ solve_schedule
  └─ resolve_order_from_m1
        ↓
route_order_type
  ├─ main → resolve_or_generate_bom
  └─ sample → sample_flow

主流程：
resolve_or_generate_bom
  → publish_bom_to_m0
  → calculate_material_requirements
  → persist_procurement_plan
  → check_material_readiness
  → create_or_update_purchase_orders
  → solve_schedule
  → persist_trace
  → END
```

关键门禁：

1. M2 BOM 草稿必须经过规定的审核/事实条件，才允许发布到 M0。
2. M3 物料匹配、缺料和治理 Gate 早于 M4 采购副作用。
3. `check_material_readiness` 未通过时，主图进入 blocked，M4 不写入采购单。
4. M5 缺权威订单、工艺、资源、物料可用性或生产单元映射时返回 `data_incomplete`，不补造默认库存、批次或产能。
5. 任何终止状态都先经过 `persist_trace`，保留步骤、原因和恢复信息。

打样子图：

```text
sample_resolve_bom → sample_execute → sample_inspect → sample_library
```

任一步状态不为 `running` 即结束；样品入库后回写统一 Trace。

### 3.4 状态和失败语义

| 状态 | 含义 | 典型处理 |
|---|---|---|
| `succeeded` | 本步骤/任务完成且后置条件满足 | 继续或汇总 |
| `needs_input` | 缺少用户必须补充的信息 | 保存 run，等待 resume |
| `needs_approval` | 需要有权限的人工批准 | 显示 Gate，批准后同一 run 继续 |
| `blocked` | 数据、权限、依赖或业务门禁不满足 | 不执行后续副作用，保留原因 |
| `partial` | 部分步骤完成，仍有可见缺口 | 输出已完成结果和后续待办 |
| `failed` | 不可恢复的执行失败 | 保存错误和证据，允许人工诊断 |
| `cancelled` | 用户或治理动作取消 | 保留审计和已经产生的结果 |

## 4. 跨模块数据桥接

| 桥接 | 来源 | 目标 | 载荷/语义 | 约束 |
|---|---|---|---|---|
| 文件上传 | Frontend/调用方 | M1 | base64 → multipart | 原始文件、SHA-256、租户、TaskID、父子任务可追溯 |
| M2→M3 | M2 | M3 | `standard_bom` → `order+bom.lines` | 只允许已审核/可用 BOM；缺事实失败关闭 |
| M3→M4 | M3 | M4 | 采购建议数组 | 先通过 M3 物料匹配/缺料 Gate；携带 tenant/site/TaskID |
| M4→M5 | M4 + M3 | M5 | 供应投影 + 订单/工艺/资源 | ETA/收货不确定时不得伪造可用物料 |
| M5→M6 | M5 | M6 | 排程指标/生产上下文 | M6 金额仍由确定性代码计算 |
| M5→M3 | M5 | M3 | `material-demand` 反馈 | 幂等受理，只记录反馈，不自动改写 MRP |
| M5→M4 | M5 | M4 | `schedule-impact proposal` | 幂等受理，调整采购需后续人工/规则确认 |

模块间不得恢复 `M3→M4` 直接 handoff；业务链统一经过 Orchestrator bridge。外部 ERP/WMS/MES/PLM 适配器属于模块或 data-adapter 自有边界。

## 5. 数据架构与所有权

### 5.1 物理存储

| 组件 | 当前用途 | 事实性质 | 备注 |
|---|---|---|---|
| M0 PostgreSQL `m0` | canonical 产品、订单、BOM、物料、供应商、设备、工艺、文档、版本、来源、证据、关系 | 权威事实 | 所有 active 工程事实先写这里 |
| M0 Neo4j/全文/向量 | 图、全文、语义检索投影 | 可重建派生 | 由 Outbox 驱动，不能绕过 PostgreSQL 写业务事实 |
| Orchestrator PostgreSQL `orch` | Job、聊天、业务流、记忆、规划中的知识/候选/工作流 | Orchestrator 事实 | 不复制 M0 业务实体 Payload |
| Redis L1/L2 | 工作记忆、会话/短期状态 | 易失/短期 | 不能作为正式知识唯一存储 |
| Chroma L4 | 当前语义记忆索引；未来已发布知识语义索引 | 派生索引 | 向量维度、租户和内容治理需单独收口 |
| M1 SQLite | 解析任务和短生命周期候选 | 临时技术状态 | M1 parser-only，不发布 active 业务事实 |
| M2 SQLite | BOM/SOP 案例、run、反馈和制品清单 | 模块运行事实 | 正式产品/BOM/文档从 M0 读取 |
| M3 PostgreSQL | 库存、MRP、分配、采购需求/齐套 | 模块运行事实 | 产品/BOM/工程参考通过 M0 API |
| M4 SQLite/SQLAlchemy | 采购建议、PO、供应商、回复、预警、追踪 | 模块运行事实 | 受控版本、租户、TaskID |
| M5 PostgreSQL + Alembic + Worker/Outbox | 排程版本、资源、派工、执行摘要、部门消息 | 模块运行事实 | 正式资源 Gate 仍需目标环境确认 |
| M6 文件/pandas | 成本计算与标准成本导入 | 计算结果 | 无独立 canonical 数据库 |
| M8 JSON/checkpointer | Project File、设计过程、报告、渲染图、BOM 草稿 | 子 Agent 运行事实 | 生产可配置 PostgreSQL |

### 5.2 M0 与 Orchestrator 的边界

M0 必须保存：

- 稳定实体身份和业务键、不可变版本、有效期。
- 字段路径、类型、单位、枚举、约束、别名和外部字段映射。
- 有方向的关系类型、端点约束、版本和证据要求。
- 原始来源内容哈希、来源出现记录、精确页码/Sheet/字段路径/区域定位。
- 候选、人工裁决、发布、失效、撤回、投影状态和审计收据。

Orchestrator 必须保存：

- 跨任务经验、错误规律、使用效果和反例。
- 输入载体、字段、物理类型、语义类型、单位、值域、质量问题等 Data Profile。
- 输入字段到 M0 字段/实体/关系的映射候选。
- Trace 子序列、人工操作和工作流修改候选。
- M0 entity/version/field/evidence 的引用，而不是复制完整 canonical Payload。

## 6. 身份、租户、TaskID、幂等和审计

### 6.1 身份与租户

- 请求上下文必须携带真实主体、租户和 data scope。
- M0、Job、Memory、Redis、Chroma、模块业务库、缓存和投影均应按租户/范围隔离。
- 权限检查由确定性代码执行；LLM 只能提出动作，不能决定越权或替代审批人。
- 用户范围、项目范围、租户范围的知识提升必须显式授权，不提供跨租户自动晋升。

### 6.2 TaskID

- 根业务入口创建新的 Tracking TaskID。
- 下游模块复用并透传同一个 TaskID；不能用 module job id、request id 或 trace id 代替。
- 异步 Job、消息、Outbox 必须在移交前持久化 tracking_task_id。
- 同一个 `(task_id, idempotency_key)` 加同载荷为成功重复；同键不同载荷必须是 `IDEMPOTENCY_CONFLICT`。

### 6.3 事务与 Outbox

正式事实发布的同一事务顺序：身份/权限/幂等 → Schema/字段版本 → 稳定业务键 → 实体和版本 → 来源/证据/关系 → 审计事件 → projection Outbox。

投影失败不能回滚已经提交的 canonical 事实，但必须记录可重试状态。API 启动时不应创建或修改业务表，Schema 变化必须通过有序迁移。

## 7. 记忆、知识和自进化架构

当前记忆层：

```text
L1 工作记忆/当前上下文：Redis
L2 会话/任务短期状态：Redis
L3 可持久历史与作业记录：Orchestrator PostgreSQL
L4 语义相似召回：Chroma（派生索引）
```

已确认目标闭环：

```text
Job/Chat/Flow/Input
  → Observation Hook
  → PostgreSQL sources + candidates + evidence
  → Background Promotion Worker
  → Published Knowledge 或 Workflow Proposal
  → 权限过滤的 Retrieval Context / 人工审批弹窗
  → Planner 使用 / Workflow Version Registry
  → 使用结果、反例、暂停、回滚
```

晋升规则：

- 首次出现必须进入持久化候选区。
- 普通候选至少在 3 个独立任务/输入中出现，才取得晋升检查资格。
- M0 正式版本、模块正式 Schema/错误码、人工纠正后成功结果可以走强证据通道。
- 所有候选还必须通过范围、权限、来源可访问、无未解决反例、版本有效和敏感内容检查。
- 操作模式达标后只能生成受限工作流候选；必须人工批准后才创建正式工作流版本。

首版明确不做：独立测评器、黄金样本平台、伪造数据识别、刷证据检测、存储额度/计费、复杂 shadow/canary、Agent 自动修改源码/Prompt/权限/M0 物理 Schema。

## 8. 前端、网关和运行时

前端职责：

- 只提交根请求或显示由 Orchestrator 返回的步骤状态。
- 展示统一人工 Gate：允许、拒绝、暂停修改、继续运行。
- 展示订单/物料/采购/排程/成本的聚合追溯和 DataRef 深链。
- 未来增加知识查看、更正、暂停、删除和工作流候选审批弹窗。

网关职责：

- `/api/<module>/*` 路由到模块服务。
- `/api/orchestrator/*` 路由到统筹服务。
- 新工具接入必须同步模块 `tool.json`、编排器声明、网关路由和 Orchestrator `config.py/compose`。

运行时边界：

- 生产应用镜像变量使用 `${MODULE_IMAGE:?MODULE_IMAGE is required}`，实际镜像由外部发布系统分配。
- runtime/build/dev Compose 三份契约分离；文档更新本身不改变 runtime contract。
- M1 GPU、DWG 转换器、MinerU/Instructor/VLM、M5 正式资源、M8 LLM/checkpointer、外部 ERP/WMS/MES 都是独立 readiness 项。
- 不把历史隔离环境、虚拟 `pressure_only` 资源或静态前端检查描述成完整生产验收。

## 9. 当前缺口与前置顺序

建议开发顺序：

1. 生产身份模式、真实 principal、租户和 data scope。
2. Job/Memory/Redis/Chroma 的租户隔离和数据范围隔离。
3. 将 API 启动 DDL 移到 Alembic/有序迁移。
4. 分离原始情景记忆和正式知识；确定 Chroma 租户、内容和 embedding 版本边界。
5. 让 Planner 接收 active 知识正文、适用条件和证据引用，并记录实际使用。
6. 实现 `orch_knowledge` 候选、来源、证据、晋升、失效和纠错。
7. 实现 Data Profile、字段映射候选和 M0 Registry/JSON Schema v2。
8. 实现 Trace 模式发现、工作流候选、人工弹窗、版本启用、暂停和回滚。
9. 补齐 M0–M4/M5/M6/M8 的正式客户端、契约和真实数据 Gate。
10. M7 法务接入单独立项；当前不应在架构图或功能表中视为已实现。
