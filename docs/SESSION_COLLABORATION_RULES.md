# 多 Session 协作规则

本规则是 `yunpai-gragh0903` 的并行开发约定。所有 Codex session、人工开发者和发布操作都遵守它。项目事实源仍是 `.project-to-act/`，本文件只定义协作边界和操作流程。

## 1. 分支与工作目录

- `main` 只读，禁止 session 直接提交、强推或部署。
- `dev` 是集成分支；只有集成负责人可以向它推送已经验收的提交。
- 每个 session 使用唯一分支：`dev/<session-id>-<topic>`，例如 `dev/s03-scroll-layout`。不同 session 不得共用分支。
- 每个分支使用独立 worktree。禁止两个 session 在同一个工作目录同时编辑或运行会生成构建产物的命令。
- 开工前执行 `git fetch --all --prune`，从最新目标基线创建分支；不要从另一个 session 的未提交工作树复制文件。

## 2. 文件认领（Ownership）

- 开工前在 `.coordination/claims/<branch>.md` 登记：session ID、负责人、分支、目标、允许修改的路径、开始时间和预计结束时间。
- 一个路径或路径模式同一时间只能被一个 session 认领。需要跨边界修改时，先停止编辑并由双方在各自 claim 文件中记录交接。
- 不要修改其他 session 的未提交文件；发现工作树变化时先 `git diff` 和 `git status`，保留原改动并报告冲突。
- `.project-to-act/` 管理文档按段落认领；同一文档没有明确交接不得并行写入。
- 完成或放弃任务后删除自己的 claim 文件，并在提交信息中留下对应 session ID。

## 2.1 实时 Session 报告（强制）

- 每个 session 必须维护自己的报告：`reports/sessions/<session-id>.md`。不同 session 绝不共用或覆盖同一份实时报告。
- 报告在开工时创建，之后每个有效工作节点立即更新，而不是等任务结束才补写。至少记录：时间、当前目标、正在修改的文件、已完成修改、命令/测试结果、阻塞与风险、下一步。
- 修改文件前先写“计划修改”；修改后写“实际修改”和 commit。发现冲突、基线变化、测试失败或线上异常时，必须先记录再继续。
- 报告只写脱敏摘要、路径、commit、run/task ID 和证据位置；禁止写密钥、令牌、完整用户数据或未经脱敏日志。
- session 结束时在报告顶部标记 `状态：已交接/已阻塞/已取消`，并写明最终 commit、未完成事项和接手人。报告本身必须随代码提交。

## 3. 提交与合并

- 一个提交只解决一个问题，提交信息使用 `<type>: <summary>`，并包含 `Session: <session-id>` trailer。
- 提交前必须检查 `git diff --check`、相关 typecheck/test/build，以及受影响的运行验收。
- 不使用 `git reset --hard`、`git checkout --`、`git clean -fd` 或 `push --force` 清理别人的改动。
- 集成前把目标分支最新提交合并到自己的分支；解决冲突时保留双方意图，并在报告中记录决策。
- 集成负责人只 cherry-pick 已验收提交，不直接复制文件。合并后重新跑最小回归集。

## 4. 线上发布

- 只有发布负责人可以操作 GB10 的 `current`、进程或数据库；普通修复 session 不直接发布。
- 发布输入必须是已推送分支上的明确 commit，先创建新 release，再切换 `current`；不得在旧 release 上原地改文件。
- 发布前后记录 release、静态资源 hash、health、回滚目标和验证时间。数据库只复制，不覆盖或删除。
- 同一时间只允许一个发布操作。发布负责人须在 claim 中登记 `DEPLOY_LOCK`，完成后释放。

## 5. 测试与证据

- 浏览器验收、截图、日志和报告按 session 单独存放，例如 `reports/s03-scroll-layout/`。
- 报告只记录脱敏摘要、run/task ID、commit、命令退出状态和证据路径，不写密钥或完整用户数据。
- 未运行、失败或过期的检查不能标记为通过；发现线上与本地不一致时，以线上实际资源和进程为准并暂停发布结论。

## 6. 冲突与交接

- 发现同一文件被认领、基线变化或线上状态变化时，立即停止相关写入，发送冲突说明，不擅自覆盖。
- 交接必须包含：当前分支/commit、已改路径、未完成事项、测试结果、已知风险、下一步和证据位置。
- 用户的新指令优先于旧 session 计划；路线变化先写入项目账本，再继续实施。

## 7. Session 开始/结束清单

开始：读取 `PROJECT_OVERVIEW.md`，按任务读取项目账本；确认基线；创建唯一分支和 worktree；登记 claim；创建并填写自己的实时报告。  
过程中：每个有效工作节点更新报告，先记录计划再编辑，测试失败或冲突立即记录。  
结束：运行适用检查；补齐报告结论；提交并推送；更新进度/版本/验收记录；删除 claim；交接 commit 和证据。
