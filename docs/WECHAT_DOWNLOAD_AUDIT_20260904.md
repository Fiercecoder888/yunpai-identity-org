## 4. 仍未核实到的生产事实

在个人微信、企业微信邮件缓存、下载目录和相关压缩包的文件名/表头级复核后，以下内容仍没有找到可直接用于生产放行的实体数据：

- 全厂生产人员主表（稳定 `person_id/worker_id`）、技能/资格证书及有效期、可操作工序。
- 人员到工位/工序的生效绑定、并行上限、替补关系。
- 工厂生产班次、工作时段、休息/节假日、请假和加班例外日历。
- 稳定的 `station_id/work_center_id`、工序到工位绑定、并行槽位和生产单元边界。
- 当前订单行/工序/批次级 WIP：剩余量、当前工位/人员/设备、开始/结束时间、质量状态和观测时间。
- 设备能力、效率、维护/停机历史以及设备与工位的当前绑定。
- 正式批准路线的版本、生效期、审批引用和产品到路线映射。
- 物料批次、分配/锁定/QC 状态，以及逐 PO 承诺交期和收货状态。
- MES/执行事件：派工确认、开工、完工、良品/报废、停机原因和幂等事件 ID。

`TEST-*` 工位/人员/WIP 夹具和代码包中的 schema、示例 JSON 只证明系统合同或测试能力，不能补足以上生产事实。

## 5. 修正后的结论

不能再说“微信下载目录没有这些数据”。正确结论是：目录里有大量真实制造原始资料，订单、BOM、库存、采购入库、供应商、设备/模具、SOP/IE 时间、手工排产和历史产出均已找到；但关键资料仍是分散、半结构化或历史汇总，尚未形成可审计的生产 snapshot。

因此，真实 PMC 目前仍不能据此生成可直接派工的完整正确工位排程。它可以做候选分析、手工排产对照和数据质量阻断；只有补齐人员/技能/工位绑定、生产日历、当前 WIP、能力与批准路线，并完成快照版本和执行回传后，才可重新验收 `production_blocked=false`。
