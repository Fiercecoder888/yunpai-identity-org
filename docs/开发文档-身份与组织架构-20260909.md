                            │ Cookie: yunpai_session (HttpOnly)        │ POST /runs/stream (NDJSON)
                            ▼                                          ▼
   ┌───────────────────────────────────────────── src/yunpai_langgraph/api.py ───────────────────────────────┐
   │ /api/auth/*      login logout me config bootstrap-status register-admin change-password                  │
   │ /api/identity/*  catalog org org/derive roles bindings users users/{id} reset-password resolve authz     │

   └───────┬──────────────────────────────┬───────────────────────────────┬───────────────────────────────┘
           │                              │                               │
           ▼                              ▼                               ▼
  identity.py (IdentityStore)     graph.py + agents.py            tool_permissions.py
  权限目录/角色种子/组织树/绑定     Planner→Worker→Reviewer         工具→权限 code 映射
  resolve()/authorize()/审计       preflight / 人话回复            assert_full_coverage()
           │                              │                               │
           │                              ▼                               ▼
           │                      registry.py ToolRegistry.call() ── 硬闸 ──► ToolForbiddenError(403)
           ▼                              │
   sqlite：identity.sqlite                ▼               sqlite：runs.sqlite

要点：**鉴权两条独立链**——`/api/identity/*` 管理面走 `authorize()`（权限 code 级），对话面走 `ToolRegistry.call()` 的工具级硬闸；两者共用 `identity.py` 同一份角色/权限事实源。身份类工具**只受工具闸管**，不再叠加 pre-execution 授权门（见 4.4）。

## 4. 逐模块设计

### 4.1 厂长注册与登录闭环

**前端入口**：`frontend-yunpaizhisuan/src/auth/AuthBoundary.tsx`

渲染顺序（`AuthBoundary` 内）：`loading/idle` → 转圈；`error` → 「身份服务不可用」+ 重试；`!me` → `needsBootstrap ? <RegisterAdminPage/> : <LoginPage/>`；`me.must_change_password` → `<ChangePasswordPage forced/>`；否则放行主应用（并挂 `SessionExpiryNotice` 与 `OrgGuideGate`）。

`VITE_ENABLE_DEMO_ROLES=true` 时 `isDemoRoleEnabled()` 直接放行、跳过鉴权（仅本地演示；交付/联调必须关掉）。

**接口层**：`frontend-yunpaizhisuan/src/auth/authApi.ts`

| 函数 | 端点 |
|---|---|
| `getAuthConfig` | `GET /api/auth/config` |
| `getBootstrapStatus` | `GET /api/auth/bootstrap-status` |
| `registerAdmin(payload)` | `POST /api/auth/register-admin` |
| `loginUser(userId, password)` | `POST /api/auth/login`（**字段名是 `user_id`**，不是 `username`） |
| `logoutUser` | `POST /api/auth/logout` |
| `getAuthMe` | `GET /api/auth/me` |
| `changePassword(oldPassword?, newPassword)` | `POST /api/auth/change-password`（省略 `old_password` = 首登强制改密场景） |

**后端实现**：`src/yunpai_langgraph/api.py`

- `GET /api/auth/bootstrap-status` → `auth_bootstrap_status()`：`needs_bootstrap = identity_store.count_users(tenant_id=tenant) == 0`，同时回 `user_count` 与 `company_name`。
- `POST /api/auth/register-admin` → `auth_register_admin()`，一次事务里做完 4 件事：
  1. 幂等闸：`count_users() > 0` → `409 ALREADY_BOOTSTRAPPED`（之后新增账号只能由厂长在账号管理里分配）；
  2. `upsert_org(org_id="company", org_type="company", source="manual")` 建公司根；
  3. `create_user(...)` 建账号（`must_change_password=0`）；
  4. `bind_user(role_codes=list(BOOTSTRAP_ADMIN_ROLES))`，`BOOTSTRAP_ADMIN_ROLES = ("factory-director", "org-admin")`（`identity.py`），即首个管理员**同时**是厂长与组织管理员；随后签发会话 Cookie 自动登录。
  - 校验：`422 INVALID_REGISTRATION`（公司名空）、`422 INVALID_USER_ID`（正则 `^[A-Za-z0-9_.@-]{3,64}$`）、`422 WEAK_PASSWORD`（< 8 位）。
- `POST /api/auth/login` → `auth_login()`：`login()` 失败统一 `401 INVALID_CREDENTIALS`（不区分用户不存在/密码错）；成功签发 Cookie `yunpai_session`（`httponly=True, samesite="lax"`）。
- `GET /api/auth/me` → `auth_me()`：受信头或会话任一可用；否则 `401 AUTHENTICATION_REQUIRED`。返回 `principal{actor,tenant_id,roles,source}` + `display_name` + `must_change_password` + `resolve()` 全量（roles/role_names/permissions/permission_scopes/org_id/org_path）。
- `POST /api/auth/change-password` → `auth_change_password()`：**是否要当前密码以库中 `must_change_password` 为准，不信任请求体**——为 1 时免当前密码；为 0 时缺 → `422 OLD_PASSWORD_REQUIRED`、错 → `403 INVALID_CREDENTIALS`；成功后置 `must_change_password=0`。

**会话实现**：`src/yunpai_langgraph/auth.py`

- `hash_password` / `verify_password`：标准库 `hashlib.scrypt`（N=16384,r=8,p=1），哈希串自带参数标签 `scrypt$N$r$p$salt$hash`（零新增依赖，后续可迁 bcrypt/argon2）。
- `sign_session_token` / `verify_session_token`：HS256 签名令牌（`base64url(payload).base64url(HMAC-SHA256)`），payload `{tenant_id,user_id,iat,exp,jti}`；默认 TTL 12 小时（`YUNPAI_SESSION_TTL_SECONDS` 可覆盖）。
- `session_from_token`：**每请求回查用户状态**，账号被停用后旧 Cookie 立即失效（下一请求 401），无需会话黑名单表。
- `generate_password(10)`：一次性初始密码，字符集去掉 `0/O/1/l/I` 等易混字符，服务端只落哈希。

**验证方式**

- 后端单测：`tests/test_change_password_api.py`（改密免当前密码/新旧密码分支）、`tests/test_runs_isolation.py`（会话与租户隔离）。
- 手工：`GET /api/auth/bootstrap-status`（空库 → `needs_bootstrap=true`）→ 页面填 5 个字段 → 提交 → 落到应用壳；二次注册应得 409。

### 4.2 组织架构（三层 + 推荐引导）

**组织模型**：`src/yunpai_langgraph/identity.py`

- `ORG_TYPES = ("company", "dept", "team")` —— 公司根 / 部门 / 班组三层。
- `IdentityStore` 相关方法：`upsert_org`（ON CONFLICT 更新，幂等）、`org_tree`、`org_path`（根→节点，最长 16 层环防护）、`org_usage`、`delete_org`（有子节点/账号/绑定 → `ValueError` → 接口 409 `ORG_IN_USE`）、`derive_org_from_workers`（花名册 → 两级树，`source='derived'` 不覆盖 `manual`；**`line` 产线层暂不派生**）。
- 名称归一化：`normalize_dept_name()`（去空白、剥「部」后缀差异，只用于合并判断）、`split_dept_field()`（一人兼多部门按 `、，,/` 切分）。

**组织管理接口**（`api.py`，全部要 `identity.admin`）：

| 端点 | 处理函数 | 说明 |
|---|---|---|
| `GET /api/identity/org` | `identity_org_tree` | 返回 `{tenant_id, org:[…]}`（**不是裸数组**） |
| `POST /api/identity/org` | `identity_org_upsert` | 手工建/改节点，`source="manual"` |
| `POST /api/identity/org/derive` | `identity_org_derive` | 从 M0 canonical worker 实体派生；无实体 → `409 NO_WORKER_ENTITIES` |
| `DELETE /api/identity/org/{org_id}` | `identity_org_delete` | 有占用 → `409 ORG_IN_USE`；不存在 → `404 ORG_NOT_FOUND` |

**推荐引导（AI 推荐 + 人工确认落库）**

后端：`src/yunpai_langgraph/guided_chat.py`（`handle_message`，在 `api.py` 里以 `handle_guidance_message` 导入）+ `llm.py` 的 `QwenRouter.guide_chat()`。

- `GET /api/guidance/presets` → `guidance_presets()` 回 `SCALE_OPTIONS` 三档：小规模（30 人以内）/ 中规模（30~200）/ 大规模（200 人以上，分工较细）。
- `POST /api/guidance/chat` → `guidance_chat()`：需 `identity.admin`；把花名册（`_load_workers()` 从 `YUNPAI_M0_DB` 的 canonical worker 实体取，或请求体显式 `workers`）交给模型；`state` 是**客户端回传的不透明 JSON**（服务端无会话表）。
- 模型契约（`llm.guide_chat` 返回）：`{ok, reply, scale, needs_scale, confirm, departments, assignments, scale_departments}`。
- 代码侧只做确定性的三件事（`guided_chat.py`）：
  1. `sanitize_departments()` 去重去空；`sanitize_assignments()` 用 `_ROLE_CODES` 白名单过滤角色、姓名非空才保留（`dept`/`manager` 仅用于前端画图，不入库）；
  2. 首开（`needs_scale` 或无 `scale`）→ 返回 `scale_departments` 三档部门名单 + `options=SCALE_OPTIONS`，**不写库**；
  3. **只有 `decision["confirm"]` 为真才调 `_apply()` 写库**：先 `company` 根，再按 `dept:<归一化名>` 建部门（`parent_id="company"`, `source="manual"`），再 `bind_users_bulk()` 绑人。模型不可用 → `_model_unavailable()` fail-loud，**不静默回退到写死规则**。
- `GET /api/identity/catalog` → `guided_setup.catalog_payload()`：只读权限目录 + 种子角色（引导模型与前端共用），**不含任何岗位→角色映射或部门模板**。

前端：`frontend-yunpaizhisuan/src/features/org/OrgRecommendationModal.tsx`

- `OrgGuideGate`（挂在 `AuthBoundary` 上）：仅当 `me.permissions` 含 `identity.admin`；触发条件 = localStorage 待办标记（`isOrgGuidePending()`，由注册成功时 `markOrgGuidePending()` 置位）或 URL 带 `?org-guide=1`（演示/测试可随时重开，不需要空库；用后即从 URL 清掉）。
- `OrgRecommendationModal`：三档规模按钮（`data-testid="org-guide-scale-<small|medium|large>"`）、对话气泡（`org-guide-bubbles`）、落地按钮 `org-guide-apply`（文案「就这样，落地」）、跳过按钮 `org-guide-skip`（「跳过，直接进对话」）。
- 红线：**未点「就这样，落地」之前不写库**（`close()` 调 `clearOrgGuidePending()`，不发写请求）。

**对话建组织**：工具 `create_org_node`（见 4.3/4.4）→ `workers.create_org_node()`：`name` 必填、`org_type` 只能取 `company/dept/team`（不传按名称推断）、父节点 `_resolve_parent_id()` 先看 `parent_id`（必须是已有节点，否则 `ORG_PARENT_NOT_FOUND`）再按 `parent_name` **精确→唯一包含**匹配；同名复用不重复建；`org_id` 用 `_org_slug()` 生成（中文名回退 sha256 前 6 位）。

**验证方式**

- 接口：`GET /api/identity/org`（三层树）、`POST /api/guidance/chat`（首开拿三档 → 选一档 → 说「就这样」才落库）。
- 单测：`tests/test_org_tools.py`。
- 前端：`frontend-yunpaizhisuan/src/features/org/orgApi.test.ts`；页面 `pages/OrgStructurePage.tsx`。

### 4.3 对话分配账号（建号 / 调岗 / 查号）

**工具清单**：`src/yunpai_langgraph/manifests/m9_identity.json`（`"module": "identity"`）

| 工具 | 关键入参 | 说明 |
|---|---|---|
| `list_identity_users` | — | 本租户账号列表（账号/姓名/组织/角色） |
| `create_identity_user` | `display_name` **或** `people[]`；`user_id`/`user_id_prefix`/`role_codes`/`org_name`/`skill`/`password` | `anyOf` 二选一；多人用 `people` 数组 |
| `assign_identity_account` | `user_id` **或** `display_name`；`org_name`/`role_codes`/`role_mode`(set|add) | 调组织 / 加换角色 |
| `create_org_node` | `name`（必填）、`org_type`(company|dept|team)、`parent_name`/`parent_id` | 建组织（见 4.2） |

**Handler**：`src/yunpai_langgraph/workers.py`，4 个身份工具统一登记在模块级字典 `HANDLERS`（文件末尾的 `"list_identity_users" / "create_identity_user" / "assign_identity_account" / "create_org_node"` 四项），由 `registry.build_default_registry()` 逐项绑到注册表同名工具上。

- `list_identity_users()`：查 `IdentityStore.list_users()`，回 `users[]` + `evidence`。
- `create_identity_user()`：
  - **批量**：`payload["people"]` 非空 → 用 `_next_user_ids(store, tenant, prefix, n)` 生成 `worker001/worker002…`（前缀取 `user_id_prefix`，默认 `worker`），逐人 `_create_one()`，回 `{count, created[]}`；
  - **单人**：没有 `user_id` 但有 `display_name` → 先 `_resolve_user_id_by_name()` 查重名，**已有账号 → `NAME_EXISTS`**（人话提示「不用重复建号；要加角色就说『给 worker001 加上品保角色』」），否则自动分配账号；两者都缺 → `MISSING_USER_ID`；
  - 账号格式 `_USER_ID_RE` 不合法 → `INVALID_USER_ID`；已存在 → `USER_EXISTS`；
  - **一次性初始密码**：`auth.generate_password()`，只在返回值里出现一次（`password_returned_once=True`），库中只落 scrypt 哈希；`must_change_password=True`。
- `assign_identity_account()`：
  - 支持 `display_name` 或 `user_id`；**模型常把姓名填进 `user_id`**（「把张伟分到1班组」）→ `_resolve_user_id_by_name()` 按姓名唯一匹配回账号；
  - 同名 > 1 → `AMBIGUOUS_USER_NAME`（列出候选账号）；找不到 → `USER_NOT_FOUND`（提示「如果是新员工，可以说『给XXX建一个工人账号』」）；
  - `role_mode="add"` → 在原角色上追加并去重保序；默认 `set` 覆盖；`org_name` → 解析成 `org_id`。
- **角色归一化**：`_ROLE_ALIASES` / `_ROLE_ALIAS_INDEX` / `_normalize_roles()` 把口语和英文别名落到角色 code（`qa|qc|品保 → quality-assurance`、`组长|班长 → team-leader`、`厂长 → factory-director`…）。**只做归一化，不是意图词表**——不参与路由、不改变工具选择。

**缺参反问与多轮续接（关键设计）**

1. `src/yunpai_langgraph/slot_filling.py` → `fill_tool_args(router, *, tool, input_schema, message, history=None, partial=None, required_hint=None)`，返回 `{args, missing, question, source:"llm"|"unavailable", off_topic}`：
   - 由模型从**用户原话/历史**抽参数（提示词明确"绝不编造"）；
   - **模型自报的 missing 不可信**，最终 `missing = required - args 的键`（`_missing_of`）由代码重算；
   - 全齐 → `missing=[]`、`question=""`；模型不可用/异常 → `source="unavailable"` + 保留 `partial` + 生成中文追问；
   - **本函数永不抛异常**，调用方直接 await 即可。
2. `src/yunpai_langgraph/agents.py`：
   - `_slot_filling_gate()`：仅对 `CONVERSATION_ARG_MODULES = ("identity",)` 的工具生效；缺参时先让模型抽参，抽完还缺 → `_ask_back()` 返回 `route="chat"` + `pending_intent{tool,args,missing,question}`（`tools=[]`，**不执行工具**）；模型不可用时才退回中文词表兜底 `identity_intent_args()`；
   - `_tool_payload_missing()` 同时支持 `required` 与 `anyOf`（如 `create_identity_user` 的「姓名 or 名单」、`assign_identity_account` 的「账号 or 姓名」）；
   - `_resume_pending_intent()`：下一轮消息带上上一轮 `question` 作为 history 再抽一次；齐了 → 返回 `route="free"` + `pending_resolved=True` 继续执行；用户换话题（`off_topic`）→ 返回 None 交回正常路由；
   - `_duplicate_tool_steps()` / `_duplicate_tool_reminder()` / `_DUPLICATE_TOOL_REMINDERS`：一句话里**同一工具排了两次**（参数按工具名传，第二次会覆盖第一次）→ 直接回 chat 提醒分两步，不执行出怪错。
3. `src/yunpai_langgraph/pending_intents.py` → `PendingIntentStore`：按 `(tenant_id, conversation_id)` 落 sqlite（表 `pending_intents`），**TTL 默认 1800 秒**（`DEFAULT_TTL_SECONDS`），过期视为不存在并在读时顺手删除；读写一律容错（脏行/库打不开 → 当作没有待办）。库路径取 `YUNPAI_RUN_DB`。反问与回答之间隔两个 HTTP 请求，所以不能放进程内存。

**人话回复**（`src/yunpai_langgraph/graph.py`）

- `_tool_result_response()`：把工具结果翻译成一句中文（建号/批量建号/调岗/查号/建组织各一套模板，角色 code 经 `_ROLE_LABELS` 转中文）；建组织成功后**主动提示下一步**（「要继续建下级或另一个组织，再说一句即可，例如『在<名>下面建个班组』」）。
- `_finalize_response()`：优先级 = 工具结果总结 > 失败原因人话 > 已有回复（压过 reviewer 套话）。
- `_FRIENDLY_ERROR_HINTS` / `_friendly_error()`：把 `INVALID_USER/NAME_EXISTS/AMBIGUOUS_USER_NAME/USER_NOT_FOUND/ORG_PARENT_NOT_FOUND/TOOL_FORBIDDEN…` 转成可操作的中文提示（注意 `INVALID_USER` 必须排在 `INVALID_USER_ID` **之后**，因后者含前者前缀）。

**会话内卡片**：`frontend-yunpaizhisuan/src/features/identity/AccountToolArtifacts.tsx`

- `IDENTITY_TOOLS = {create_identity_user, assign_identity_account, list_identity_users}`；
- 渲染 `data-testid`：`account-created-card`（单条建号）、`account-created-batch-card`（批量，含 `account-initial-password` 列）、`account-assigned-card`（调岗）、`account-list-card`（账号列表）；
- **为什么要额外拉一次 run**：流式 `step_result` 里的结果是后端 `models.summarize()` 裁过的（数组只留 `{count, sample}`），拿不到完整 `created/users`，所以身份类工具改成用 `run_id` 调 `getLocalRun()`（`GET /runs/{id}`）读 run 级 `outputs[tool]`；其它工具仍用入参兜底；
- 失败步骤由 `ChatPanel` 整条走失败分支，本组件不会被挂载，**绝不把失败渲染成空卡片**。

**验证方式**

- 后端单测：`tests/test_identity_tools.py`（工具语义/别名/重名/幂等）、`tests/test_slot_filling.py`、`tests/test_pending_intents.py`、`tests/test_planner_empty_tools_route.py`。
- 前端：`features/identity/AccountToolArtifacts.test.tsx`。

### 4.4 工具级权限闸（不同角色可调用的工具不同）

**唯一事实源**：`src/yunpai_langgraph/tool_permissions.py`

- `TOOL_PERMISSION_RULES`：按「模块 + 工具名正则」把工具映射到 PR #6 已有的权限 code（M0/M1/M2/M3/M4/M5 各段，如 `m0` 读 → `data.steward`、`m1` 入库 → `order.ingest`、`m5` 求解 → `schedule.solve`）；
- `TOOL_PERMISSION_OVERRIDES`：个别修正，**身份四件套在这里**——
  `list_identity_users` / `create_identity_user` / `assign_identity_account` / `create_org_node` → `identity.admin`（只有厂长/组织管理员可调用）；
- `permission_for_tool(name, module)`：先查 override，再按正则匹配；未登记 → `None`；
- `assert_full_coverage(specs)`：**启动期**校验，注册表里任何工具缺映射就抛错拒绝启动（"漏配 = 默认放行"就是漏洞）；由 `api.create_app()` 在建 app 时调用；
- `authz_mode()`：`YUNPAI_TOOL_AUTHZ` = `off | warn | enforce`，**默认 `enforce`**（fail-closed）；`warn` 只记日志不拦（迁移用）；
- `tool_allowed(name, module, permissions, scopes)`：给 `/tools` 过滤与前端能力展示用；**映射按租户级登记，因此 `@self`/`@dept` 的窄范围授权不满足工具要求**（否则 `order.view@self` 的工人能读到全租户订单）。

**执行点（唯一硬闸）**：`src/yunpai_langgraph/registry.py`

- `ToolForbiddenError(tool, required, permissions)`：`code="TOOL_FORBIDDEN"`、`status_code=403`；
- `ToolRegistry._authorize_tool()`，在 `ToolRegistry.call()` 里**紧接** `spec` 取出之后调用（Skill 内部调用也走 `call`，所以同样受闸）：
  1. `context` 里没有 `principal` → 直接放行（内部调用/单测/CLI 保持 legacy；HTTP 入口一定带 principal）；
  2. `mode == "off"` → 放行；
  3. `required is not None and required in permissions and scopes.get(required,"tenant") == "tenant"` → 放行；
  4. `mode == "warn"` → 记日志放行；
  5. 否则 → `raise ToolForbiddenError(...)`。

**principal 贯通链路**（漏一环闸就形同虚设）

```
浏览器 Cookie/受信头
  → api._request_principal()                 （验签会话或读受信头）
  → api._run_principal()                     （effective_permissions() 算生效权限 + permission_scopes）
  → new_state(payload, principal=…)          （四处「新建 run」入口：/runs、/runs/stream、/runs/upload、/runs/upload/batch）
  → principal 随 run 落库                    （resume 走 graph.repository.get(run_id) 取回原 state，不重新注入）
  → agents.WorkerAgent.run()                 （identity_context = principal / principal_permissions / principal_scopes）
  → registry.ToolRegistry.call(name, payload, context) → _authorize_tool()
```

注：`/runs/{id}/resume` 与 `/runs/{id}/resume/stream` **不重建 principal**，直接用落库 state 里的那份；它们另有自己的 Gate 校验链（`graph.authorize_gate` + `_identity_gate_check`）。因此"谁能批准这道 Gate"与"谁能调这个工具"是两条独立判定。

**`/tools` 按人裁剪**：`api.list_tools()` 用 `_run_principal()` 拿权限，`permissions is not None` 时用 `tool_allowed()` 过滤 catalog（无身份 = 本地/内部调用，返回全量）。工人登录后 `/tools` 为空、调 `list_m1_tasks` → `TOOL_FORBIDDEN`。

**与 pre-execution 授权门的关系**：`agents.ReviewerAgent.preflight()` 对 `_IDENTITY_ADMIN_TOOLS = {list_identity_users, create_identity_user, assign_identity_account, create_org_node}` **不再叠加** pre-execution 授权门——因为该门的允许角色是 `operator/admin`，厂长无法自审；身份工具的安全边界完全由 `identity.admin` 工具闸承担（fail-closed）。注意这个常量名与 4.4 里的"工具权限映射"不是同一处配置。

**用户看到什么**：`graph._FRIENDLY_ERROR_HINTS` 里 `TOOL_FORBIDDEN` → 「当前账号没有做这个操作的权限（只有厂长/组织管理员可以管理账号）。」（措辞对查号/建号/调岗都适用）。

**厂长侧的权限来源**：`identity.DEFAULT_ROLE_SEEDS` 中 `org-admin` 角色权限 = `["identity.admin", "worker.view"]`；注册时 `BOOTSTRAP_ADMIN_ROLES = ("factory-director","org-admin")` 双角色绑定（**不改种子**：`factory-director` 本身仍不含 `identity.admin`，保持权责分离与既有断言）。

**前端权限码桥接**：`frontend-yunpaizhisuan/src/features/roles/backendPermissionMap.ts`

- `pagePermissionsForRoles(roles, backendPermissions)`：后端角色 → 前端**页面**权限码（两套 code 语义不同，做显式可审计映射而非自动推导）；
- 兜底 fail-closed：未知角色 → 空权限（页面全挡）；
- 后端 `identity.admin` → 额外授予 `org:read / org:write / account:read / account:write / role:manage / system:setup`（厂长经由 `org-admin` 拿到）。

**验证方式**

- 后端单测：`tests/test_tool_authz.py`（含 `@self` 窄范围不满足、未映射 fail-closed、warn/off 模式）。
- 冒烟：工人会话 `GET /tools` 应无工具；直接调受限工具应得 `TOOL_FORBIDDEN`（403）。

### 4.6 调用者画像 caller 注入

**问题**：对话里问"我的角色是什么"，模型拿不到"提问者是谁"，只能去调工具查别人 → 反问"请提供你的账号"。

**实现**（`src/yunpai_langgraph/api.py`）：

- `_caller_profile(request, *, tenant_id)`：有有效会话/受信头才返回画像，否则 `None`（不注入，行为与之前一致）；内容 = `{user_id, display_name, roles, role_names, org_path, org_path_ids, permissions}`。
  - `org_path` 是**组织名称**（用 `identity_store.org_tree()` 做 `org_id → name` 映射，查不到回落 id），`org_path_ids` 保留原始 id；两者都给，方便回答"我在哪个部门"。
  - 身份库异常不阻断对话（`try/except` 兜底为空）。
- `_with_caller(request, tenant_id, payload)`：有画像时 `{**payload, "caller": caller}`；**在 `/runs` 与 `/runs/stream` 两处入口注入**（`new_state(...)` 之前）。

**模型侧**（`src/yunpai_langgraph/llm.py`）：

- `_prompt()` 输出 `"caller": request.get("caller") or None`（显式 null，不是省略字段）；
- `_system_prompt()` 增加规则：请求里的 `caller` 是**当前登录人**；问"我是谁 / 我的角色 / 我有什么权限 / 我在哪个部门" → `route=chat`、`tools=[]`，**直接用 caller 回答，不要让用户提供账号、也不要调工具查自己**；caller 为空（无身份）才说明需要登录。
- 同处还有两条与人话相关的规则：chat 的 `answer` 必须是**人能直接看懂的中文**（不出现工具名/参数名/字段名/JSON/角色 code）；以及"纯能力提问 vs 礼貌请求"的区分（前者 chat，后者照做）。

**验证方式**：`tests/test_caller_profile.py`（注入内容、工人身份、不越责、匿名不注入、落库/流式事件都带 caller）、`tests/test_llm.py`（提示词含 caller 规则、`_prompt` 字段）。手工：登录后问"你好我的角色是什么"应直接答「你是 X（姓名），角色：…」，且不产生 `step_result`。

### 5.2 容易踩的契约点

1. **登录字段是 `user_id`**，不是 `username`。
2. **HTTPException 的业务 code 在 `detail` 里**：断言/前端取错时先解 `detail.code`（`authApi.authFetch` 已经这样解）。
3. `/api/identity/org` 回 `{tenant_id, org}`、`/api/identity/users` 回 `{tenant_id, users}` —— **不是裸数组**。
4. **前端 `caller` 不用传**：`caller` 由后端 `_with_caller()` 注入。注意实现细节：只有**存在有效会话**时才覆盖请求体里的 `caller`；无会话时若客户端自带 `caller` 字段会原样透传给模型（见 §7 限制 4）。
5. **`/api` 前缀双路径**：`api.py` 的中间件 `_accept_unprefixed_identity_paths` 把无前缀的 `/auth|/identity|/guidance/*` 内部映射回 `/api/...`，兼容 vite dev proxy 与 `_deploy-gb10/static_proxy.py` 的"剥 `/api`"改写；`/runs`、`/tools`、`/health` 本身无前缀，不受影响。
6. **NDJSON 事件契约**：`run_start` / `assistant_delta` / `step_start` / `step_result` / `gate_opened` / `run_error` / `run_done`；`run_done.state.response` 与 `GET /runs/{id}.response` 应一致（人话总结以落库为准）。
7. **`step_result` 是摘要过的**（`models.summarize()`：dict 只留白名单键、list 只留 `{count, sample}`）——身份类工具要完整数组必须再拉 `GET /runs/{id}.outputs`。
8. **pending_intent 落在 runs 库**（`YUNPAI_RUN_DB` 指向的 sqlite，表 `pending_intents`，TTL 1800s）；会话续接依赖 `conversation_id`，前端必须稳定复用它。

### 6.5 前端构建产物必须自检（本轮真实事故换来的规矩）

**事故经过**：2026-09-10 的一次 `pnpm build` 打印了 `✓ built in 16.38s`、退出码 `0`，但产物 `dist/assets/index-D9rE85jP.js` 里**根本没有 `/quality` 路由**——把 bundle 的路由表按字节 dump 出来，顶层 children 只有 `index` / `c/:conversationId` / `worker` / `leader` / `org` / `accounts` / `roles` / `*`。而**源码是对的**（`app/router.tsx` 里有 `path: 'quality'`，`git status` 干净）。

**后果**：`static_proxy.py` 直接托管磁盘上的 `dist/`，所以演示栈 18003 立刻服务了这份坏产物；`verify/e2e_role_landing.mjs` 从 **28/28** 掉到 **26/28（2 条 FAIL）**——「品保登录后落在 `/quality`」实测落 `/`、「工人访问 `/quality` 被拦回 `/worker`」实测落 `/`（路由不存在时被 `*` 兜底到首页）。

**根因**：**未最终定位**。当时观察到那份构建所属的源码快照缺了 6 个文件的改动（`router.tsx` / `roleConfig.ts` / `routePermissions.ts` / `sidebarConfig.ts` / `AssistantRoleLayout.tsx` / `EnterpriseAssistantPage.tsx`），疑似并发会话在同一 worktree 上做了 stash/restore；也可能只是一次批量文件系统事件。**18:54 重建后产物与 18:13 那次 content-hash 完全一致（`index-DSeyC87p.js`）**，说明源码一直是对的，只有那次构建读到了旧内容。

**规矩（每次前端构建后逐条做）**：

1. **在产物里 grep 关键路由串**——产物对不对，看字符串最直接：
   ```powershell
   $b = Get-ChildItem dist\assets\index-*.js | Select-Object -First 1
   Select-String -Path $b.FullName -Pattern 'path:"quality"','path:"worker"','path:"leader"'
   ```
   `/quality` 那条命中数应为 1。
2. **核对 `dist/build-info.json`** 的 `commit` 与 `dirty` 是否符合预期：正确的那次是 `commit=3bb4bc8…`、**`dirty:false`**；坏的那次是 `dirty:true`。
3. **跑 `verify/e2e_role_landing.mjs`**——它内置两级判定，能把两类失败分开：
   - `CODE_NOT_FINISHED`：产物里搜不到关键路由串 / `buildTime` 早于源码 mtime → **dist 未重建或未生效**（不是产品 bug）；
   - `REAL_REGRESSION`：源码就绪、产物含关键串、产物不旧，但仍然失败 → **真回归**。

> 一句话：**`✓ built in` 只是编译器说的话，不是产物的证据。** 构建后必须用「产物里的字符串 + build-info + E2E 诊断」三件套确认，尤其当 `dist/` 正在被演示栈托管时。

## 7. 已知限制与未做项

1. **Planner 侧工具裁剪未做（L2）**：模型在提示词里**仍能看到全部工具名**，只是调用时被 `ToolRegistry` 的工具闸拒绝（403 `TOOL_FORBIDDEN`）。也就是说"越权"是**执行期拒绝**，不是"看不见"。`/tools` 已按 principal 过滤，但 planner 的 tool catalog 尚未同步裁剪。
2. **`@self` / `@dept` 数据范围过滤未做**：`permission_scopes` 只被记录与用于"窄范围不满足租户级工具"这一条判定；`order.view@self` 的工人**不会**在服务端被过滤成只看自己的订单。`guided_setup.catalog_payload()` 的 note 也写明「v1 执行层按 tenant 隔离，dept 过滤待组织树链路稳定后启用」。
3. **匿名运行按 legacy 放行**：无会话/受信头时 `ToolRegistry._authorize_tool()` 直接 return、`_run_access_scope()` 返回 `None`（`/runs` 列表可见全部）。内网本地联调方便，**生产必须同时 `YUNPAI_REQUIRE_TRUSTED_PRINCIPAL=1`**（或由网关强制注入受信头），否则这个放行口仍然存在。
4. **`caller` 的注入条件**：`_with_caller()` 只在**有有效会话**时覆盖请求体；无会话时请求体里自带的 `caller` 会原样进模型提示词。影响面仅限"模型如何自述身份"（`caller` 不参与任何授权判定），但严格来说是一个可伪造字段，联网/多租户部署时应统一由网关或中间件清洗。
5. **Gate 级身份判定默认不拦**：`YUNPAI_IDENTITY_ENFORCE` 默认 `shadow`（只记审计不返回 403）；要强制需显式设 `on`。
6. **组织层级只派生到部门**：`derive_org_from_workers()` 只派生 `company ← dept` 两级，**第三层 `team` 与产线 `line` 都不派生**（数据无此维度，等工位绑定数据）；班组目前靠对话建组织/组织架构页手工添加。
7. ~~品保没有独立落地页~~ → **已于 2026-09-10 补齐**：`roleLandingConfigById['quality-assurance'].landingPath` = `/quality`，该路由渲染**与厂长相同的 `EnterpriseAssistantPage`**（按用户口径"页面暂定与厂长一样"），差别只在可见性——看不到 M1–M5 面板、没有查流程入口、不能分配账号（见 §4.5「落地页可见性边界」）。**未做**：给品保单独的业务工作台页面（M7 来料待验/抽检工作台）——当前复用对话页，品保在对话里用自然语言处理 M7 相关事项。
