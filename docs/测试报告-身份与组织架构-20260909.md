## 7. 本轮修复并验证的缺陷

### 缺陷 1：「我的角色是什么」被答成「无法查询，请提供账号」

| 项 | 内容 |
|---|---|
| 现象 | 用户问「你好我的角色是什么」→ AI 回「我目前无法直接查询您的角色信息。请问您能提供您的用户名或账号吗？」（把"自己的身份"当成要查别人） |
| 根因 | `/runs`、`/runs/stream` 的请求体里**没有任何调用者身份**，模型只能靠工具查别人，自然反问账号 |
| 修法 | ① `src/yunpai_langgraph/api.py`：新增 `_caller_profile()`（**L450**，用 `identity_store.resolve()` + 组织树名称映射产出 `{user_id, display_name, roles, role_names, org_path(名称), org_path_ids, permissions}`）与 `_with_caller()`（**L486**），注入 `/runs` 与 `/runs/stream`；② `src/yunpai_langgraph/llm.py`：`_prompt()` 输出 `caller` 字段 + 提示词规则（**L159–160**）「问『我是谁/我的角色/我有什么权限/我在哪个部门』→ route=chat、tools=[]，直接用 caller 回答，不索要账号、不调工具」 |
| 验证 | ① `e2e_chat_identity.mjs`（真实 DeepSeek，19032）**17/17 PASS**：厂长 →「你是厂长（自问厂长），角色：厂长、组织管理员。」、工人 →「你是工人（王五），角色：工人。」、**无 step_result（没调工具查自己）**、回复不含索要账号句式；② `live-19012-identity.mjs`（线上 19012）**2/2 PASS**（原文见 §6）；③ 单测 `tests/test_caller_profile.py` **7 例** + `tests/test_llm.py` 2 例 |
| 回归 | 「给张伟建一个工人账号」仍 `route=free` 并真实建号（`e2e_chat_identity` A6a PASS）；「能创建品保的账号吗」仍 chat+0 工具（A6b PASS） |

### 缺陷 2：一句话里同一工具要用两次 → 参数互相覆盖，报 `ORG_PARENT_NOT_FOUND`

| 项 | 内容 |
|---|---|
| 现象 | 「新建品质部，然后在里面建个出货检验组」→ 第一步就把「出货检验组」当父节点去找「品质部」→ `ORG_PARENT_NOT_FOUND`（两个动作共用同一工具名，后一份 args 覆盖前一份） |
| 根因 | 工具按**工具名**传参，同一工具在一个 `tools` 列表里出现两次时 args 会互相覆盖；模型又被要求"一次把多动作给全"，于是重复列同一工具 |
| 修法 | ① `llm.py` 提示词（**L148–152**）：同一工具一句话只能用一次；若一句话要求两次，`route=chat` 提醒用户分两步并给示例（多人建号用 `people` 数组例外）；② `agents.py`：新增**确定性守卫** `_duplicate_tool_steps()`（**L364**）/ `_duplicate_tool_reminder()`（**L371**）+ 提醒文案表 `_DUPLICATE_TOOL_REMINDERS`（**L357**），在 `aplan` 里命中重复即返回 chat 提醒（`route_decision.source="duplicate_tool_guard"`，**L322–329**），不再执行出怪错；③ `graph.py`：`_tool_result_response()`（**L463**）在建组织成功后主动提示下一步（**L494**）「要继续建下级或另一个组织，再说一句即可，例如「在<name>下面建个班组」」 |
| 验证 | `e2e_chat_generalize.mjs`（真实 DeepSeek，19029）**11/11 PASS** 中的 G0：「新建品质部和品质二部」→ 实测回复「一次只能创建一个组织，请分两步操作：先「新建品质部」，再补一句「新建品质二部」。」（另一次运行为「一次只能新建一个部门，请分两步操作…」）；G1a/G1b 用两句正常建成「品质部 → 出货检验组」 |

### 缺陷 3：「疑问句 → chat」过度触发，把礼貌请求也吞了

| 项 | 内容 |
|---|---|
| 现象 | 早期规则把所有疑问句都判成 chat，导致「能不能帮我把刘福的品保角色加上？」这类**点了对象+动作的礼貌请求**被当成闲聊，不去执行 |
| 根因 | 提示词没有区分"提问"与"用商量的语气下指令" |
| 修法 | `llm.py` 提示词（**L107–118**）把疑问句拆两类：① **纯能力/可能性提问**（没点明具体对象）→ `route=chat`、tools=[]；② **礼貌请求**（点了人名/账号/组织名 + 明确动作）→ 照做 `route=free` 并给 args，并补 3 条礼貌请求 few-shot |
| 验证 | `e2e_chat_generalize.mjs` **11/11**：G4a「能不能帮我把刘福的品保角色加上？」→ `route=free` + `assign_identity_account`，且实测 roles 变为 `["team-leader","quality-assurance"]`（PASS）；G4b「能不能给员工建品保账号」→ `route=chat` + 0 工具（PASS） |

### 缺陷 4：chat 回答泄露内部话（工具名 / 角色 code）

| 项 | 内容 |
|---|---|
| 现象 | 泛化测试跑出：「您可以通过 **create_identity_user** 工具为员工创建品保账号，角色代码为 **quality-assurance**。…」——把工具名、参数名、角色 code 直接吐给用户 |
| 根因 | 提示词只约束了路由与 args，**没有约束 `answer` 的表达方式**；模型自然沿用了系统提示词里的内部术语 |
| 修法 | `llm.py` 提示词新增规则（**L157**）：`route=chat` 的 answer **必须是人人能看懂的中文**——不出现工具名/参数名/字段名/JSON/角色 code（要写「品保」「组长」「工人」），也不提「工具」「接口」「系统」；同时在泛化 E2E 新增**断言 G4c**「chat 回答不泄露工具名/角色code/参数名」做永久回归拦截 |
| 验证 | `e2e_chat_generalize.mjs` 复跑 **11/11 PASS**；修复后 G4b 实测回复：「可以的，我可以为员工创建品保账号。请问您想为哪位员工创建？请提供员工姓名或账号信息。」（原泄露句式消失）；G4c PASS |

### 缺陷 5：品保快捷导航文案与「品保看不到 M1–M5」这条硬约束直接矛盾（且是死链）

| 项 | 内容 |
